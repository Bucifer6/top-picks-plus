## Findings

1. **Should fix – docs/decisions.md D93; docs/data.md plays.json (import marker); C78.** The import marker only stops a second import when it belongs to *this* run ("a marker for its own run"). A new run with a different `runId` that finds `playbackReportingImported` false still imports again, even though plays.json already holds a marker and the imported rows. Three ways this happens: (a) a run whose state.json save keeps failing ends `failed` at the import step, and the next run re-imports; (b) run.json damaged and renamed (D32), so the next run is new; (c) state.json deleted by the owner (finding 2). The result is doubled viewer-days for the import window. Simpler and safe: any import marker in plays.json means the import is done, so the next run just sets the flag. The resume rule then becomes a special case of that. Also add a C78 case for a marker from another run.

2. **Should fix – docs/decisions.md D93 (damaged state.json); docs/data.md state.json; spec F9; C94. Owner-level: backups, hard to undo.** The only recovery offered is "restore state.json from a backup", but nothing in the plan makes or names a backup of `programdata\plugins\TopPicksPlus\`. The other choice, deleting the file, resets all three flags. That repeats the takeover. It also repeats the import with a new `listeningSinceUtc`, so the window now overlaps plays already logged live, and finding 1 means the marker won't stop it. Runs stay refused until the owner acts. The builder doesn't have to guess (the behaviour is fully defined), so this isn't a Blocker. But the owner would face a choice with no safe answer, on a matter the owner has to decide. Either say where the backup comes from, or let the plugin rebuild the flags from evidence it already has: an import marker in plays.json means imported; a non-empty managed.json or run.json means takeover done. Then deleting state.json becomes safe, and the report can say so. Same kind of gap as backlog B7 (damaged managed.json).

3. **Nit – docs/checks.md C92; docs/decisions.md D90, D80.** Leftover old wording. C92's second half still says `` `TakeoverDone` false``, and C92 has no "[Amended by D93]" mark. D90's body reads `TakeoverDone` with no D93 mark (D41, which it amends, is marked). D80's body still says the resume detects an earlier import by rows "with an import `origin`". Its D93 mark mentions the marker but doesn't say the marker replaces that test. decisions.md uses PascalCase flag names and data.md uses camelCase. That's harmless, but it's worth one line saying they are the same fields.

4. **Nit – D94(b), C44, D86 step 3, spec F1.** With the old plugin loaded, start-up "writes nothing". So the report's "uninstall the old plugin" message must come from memory, as D85 already says for `dataNewer`. That isn't stated for `oldPluginLoaded`. Pressing Run now in that state does write `lastRefusal` (D94a). So C44's "nothing is written" only covers the restart, yet D86 step 3 does C44 and C19 (which runs the task) in the same session. Say that the start-up refusal is held in memory, and that C44 is checked before C19.

5. **Nit – D93 (damaged state.json).** It says play logging and watched sync carry on, but doesn't say whether the order guard does. Probably yes, as nothing in it depends on the flags, but it should be said, as D85 does for "data newer".

6. **Nit – D94(a), data.md run.json `lastRefusal`.** "Only `lastRefusal` is written; the other fields are left exactly as they were." For `alreadyRunning`, though, a working run is also saving run.json at each step change. It isn't said how the two writes are kept from wiping each other: who does the read-modify-write, under what lock, and whether the working run's next save keeps the `lastRefusal`. This is an older issue (D31, C38), but D94 now states the rule more strictly.

7. **Nit – docs/backlog.md (rule from D92).** No backlog item stops a chunk being built or tested, so there is no Blocker in disguise. But D92 lets each chunk's builder "fix or decide" its items. B7 (recovery from a damaged managed.json, where deleting it leaves copies unmanaged for good) and B4 (proof steps on the owner's server) touch matters the owner decides. Mark them as needing the owner's say rather than the builder's.
