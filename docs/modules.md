# Parts (modules)

One DLL, `TopPicksPlus.dll`. Each part is a folder and namespace under `src/TopPicksPlus/`. The plugin root (`TopPicksPlus` namespace: the plugin class) only wires parts together; no part may use a root type (the boundary check bans them). Files a part needs (page HTML, font) live inside that part's folder. Changed 2026-11-08 by D28 (owner's choice), D29 and D34 (takeover and import removed; Store no longer uses System.IO.Compression); spec v6 (D39: no part changes watched state) added front-door actions inside existing walls, with no new "may use" link; spec v7 (D44–D46) likewise; spec v8 (D51–D53) removed folder resolving (no native calls anywhere) and changed no wall.

**Root** (`TopPicksPlus` namespace): the plugin class and the start-up entry point. It may use every part, only to build them and wire them together (its settings source is a small class that reads and saves the Settings configuration class and turns it into Logic's settings record); no part may use a root type (the boundary check bans them).

**Banned for every part:** `System.Net` (no network calls, F9), `System.Diagnostics.Process` (no other programs started), SkiaSharp everywhere except Artwork, and the Emby SDK (`MediaBrowser.*` and `Emby.*`) everywhere except EmbyBridge and Settings. Logic and Artwork may not touch files at all (`System.IO.File`, `Directory`, `FileStream`, `FileInfo`, `DirectoryInfo`); Logic may not use `Task`/async either. NetArchTest matches by name prefix, so the `System.IO.File` ban also bans types such as `FileNotFoundException`: Artwork therefore catches plain `Exception` around its SkiaSharp calls, and the ban stays as it is. Every plugin type must be in the root namespace or a part's namespace. Read-only for EmbyBridge's file access, "Top Picks folder and staging only" for Run, and Run using only EmbyBridge's interfaces (never its concrete classes) can't be checked by the tool; the Stage 7 review checks them.

**Tests** (`tests/TopPicksPlus.Tests`, never shipped) may also use NSubstitute and Mono.Cecil (D47), pinned and locked like every other package; the first EmbyBridge build chunk adds both to the test project, with the B-layer tests and C49's Cecil scan.

**C49's Cecil scan (D47):** reads the built DLL and fails if any EmbyBridge method calls an Emby SDK method on the **ban list**: every method of `MediaBrowser.Controller.Library.IUserDataManager` whose name starts with `Save` or `Update`, `MediaBrowser.Controller.Session.ISessionManager.OnPlaybackProgress`/`OnPlaybackStopped`, every item `Delete…` method on `MediaBrowser.Controller.Library.ILibraryManager`, `ILibraryManager.AddVirtualFolder`/`RemoveVirtualFolder`, and every method of `MediaBrowser.Model.IO.IFileSystem` that writes, moves or deletes, plus any `System.IO` method that writes, moves or deletes. It also fails if **any** plugin method, in any part, is a native call (P/Invoke, D52). The ban list is matched by full type and method name, never by the plugin's own names (so Run's resume hook is untouched). The scan also fails if a banned name no longer exists in the pinned SDK (so a renamed method can't slip through silently), and its fixture class making one banned call must make it fail (card 0002). The first EmbyBridge chunk confirms each name in the SDK before relying on it; a name that isn't there is corrected here in the same pull request, and the owner is told.

A new part, or a new "may use" link, needs the owner's approval and an update here, in the READMEs and in BoundaryTests.cs.
