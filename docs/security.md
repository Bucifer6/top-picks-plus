# Security (level 1 – Personal)

| Item | How it is met |
|------|---------------|
| Secrets only in .env, never committed | The plugin needs no secrets. .gitignore excludes .env, keys and certificates |
| Secret scan | Before every commit Claude runs a pattern check on the staged changes (keys, tokens, passwords, private-key blocks): `git diff --cached -U0 | grep -E '^\+' | grep -nEi '(api[_-]?key|secret|token|passw(or)?d)\s*[:=]\s*["'"'"']?[A-Za-z0-9/+_\-]{12,}|-----BEGIN [A-Z ]*PRIVATE KEY|ghp_[A-Za-z0-9]{20,}|AKIA[0-9A-Z]{16}|xox[baprs]-'`. Nothing printed (exit 1) means clean. gitleaks then scans the commits being pushed (on a pull request, all of its commits) on every build (build.yml); it does not rescan the whole history each time. The full gitleaks scanner can't be run in the cloud workspace (outside downloads are blocked). |
| Dependency vulnerability audit | `dotnet list package --vulnerable` fails the build (build.yml), and a weekly scheduled build repeats it. Restores are locked to the committed lock files (D31) |
| Backups with a tested restore | Before first install and every release: a safety copy of Emby's `data`, `config`, `root` and `plugins\configurations` folders, kept on the server PC only in `C:\Users\Admin\EmbySafetyCopy\` (other standard Windows accounts can't read it; administrator accounts can, D56) (it holds sign-in data, every user's ID and their full watch history, unlike the plugin's own backups), the 2 newest kept, with one restore tried before the first install (D48, D54, C81). Before first install: old plugin DLL and settings backed up on the Desktop (D17). At every run (F4 step 3): plays.json with `"today": []` (no user IDs, still loadable) and TopPicksPlus.xml into `backups\YYYY-MM-DD-HHMMZ\`, 8 kept (D37). Copies and the managed list are never restored: the fix for a damaged managed.json is the install steps (empty top-picks, delete managed.json). Restore steps: the safety copy in releases.md, the plugin's backups in spec F9; C30 tries the fix; C63 tests a plays.json restore and the owner tries one before release |
| Safe error messages | Run report says what failed in plain words; stack traces never on the page; on any path that concerns a user (plays, user data) the log line holds only where and the error type, never the message (spec F4, C69). Every plugin API action checks for an administrator on the server first and refuses anyone else with no data (F8, C26, C70); actions that change something accept POST only |
| Bad input refused, never a crash | Damaged data files (unreadable, unknown version, or any field breaking data.md's rules) are handled as spec F9 says (D37: managed.json refuses every run; state.json reset; run.json renamed aside; plays.json deleted), C30, C51, C62. Every hook, timer, listener and API action catches every error, so nothing reaches Emby (F4). Names from Emby go through SafeName and .nfo files through an XML writer (F3, C28); a path with a line break is left out; bad pins show "missing" (F2) |
| Deletes only what it made | F9 delete guard: managed only (and files someone put inside a managed folder, the one exception), single names for everything the plugin writes, found entries handled only by their exact path (D57), full path inside the Top Picks folder or staging with no junction or link on the way, never deleting through one; the Top Picks and data folders themselves may not be links (C18, C27, C52). A disconnected drive refuses the run (D25, C29). Emby items' dates and artwork are only changed inside the Top Picks folder (C59); the plugin never changes anyone's watched state (D39, C49) |
| Personal data | None kept (D21, D33): only daily viewer counts per title, 90 days; user IDs exist only for the current day's plays and are deleted within minutes of the day ending; backups never contain them; a damaged plays file is deleted at once (D37). The plugin never writes a user ID into a log line or error message, and play-path log lines never name a title (spec F6). Note for the owner: a backup of the whole PC (or Windows shadow copies) taken during the day can still capture that day's plays.json with user IDs. Stays on the server |
| No network | The plugin makes no network calls. `System.Net` and `System.Diagnostics.Process` are banned for every part by the boundary check (BoundaryTests.cs) |
| Build integrity | Actions pinned to commit IDs; the DLL's checksum is taken and the DLL kept before any test runs (D31); releases only from tags on main. Build attestation is skipped at level 1. Owed before release (Stage 8): protecting main on GitHub (no direct pushes; an owner setting, since D27 lets Claude merge); pinning the toolchain (.NET SDK version, runner image, gitleaks and Stryker versions) instead of floating versions; running the dependency audit before the tests. Missing lock files fail the build |
| Settings and page input | Every saved value checked on the server (F8); text from Emby shown as plain text only (F8, C54) |
