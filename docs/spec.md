# Top Picks Plus – spec (v11, 2026-11-08)

**Purpose:** Every week, fill the "Latest Top Picks" row on the Emby home screen with the 10 titles people are watching most, numbered 1–10 in the right order every time, with no manual step. The owner can pin titles if they want to.

**Replaces:** the old third-party plugin Emby.TopPicks (file `Emby.TopPicks.dll`), abandoned and closed source. It orders the row by writing a "date added" into each title's .nfo file. Emby only reads that date the first time it sees a title, so when last week's folders are still there the order breaks (card 0001).

**Install (D34):** the owner uninstalls the old plugin, empties the top-picks folder by hand (its folders are only copies) and installs this plugin. Exact steps are in docs/releases.md. The plugin never adopts or imports anything from the old plugin: the first week's row is pins plus the newest titles, and real viewing takes over from the next week.

**Rigour level:** 1 – Personal: a home Emby server with a handful of users. No viewing history is kept: only how many people watched each title on each day, for 90 days (D21, D33).

## Words used here
- **Source title:** a real movie or series in the owner's normal libraries (for example N:\Movies, K:\Series). **Source item:** a source movie or source episode (the thing with a video file).
- **Emby ID:** an item's `Id` exactly as Emby's own API gives it, as text (on Emby 4.10 a number written as text). The first EmbyBridge build chunk confirms which Emby property this is (C34).
- **Movie or TV library:** an Emby library whose content type is "movies" or "tvshows". Mixed or other libraries are never used as sources.
- **Copy:** the Top Picks version of a source title: a folder of .strm, .nfo, subtitle and image files in the Top Picks folder. A .strm file is a one-line text file holding the full path of the real video file; Emby plays the real file through it. **Copy item:** the Emby item Emby makes for a copy (a copy movie, a copy series, or a copy episode).
- **Copy-looking folder:** a folder directly inside the Top Picks folder that holds a .strm file, in itself or one level down (a season folder). Used only by the missing-managed.json rule (F9).
- **Programdata:** Emby's data folder, given by Emby at start-up (here `C:\Users\Admin\AppData\Roaming\Emby-Server\programdata`).
- **Top Picks folder:** always `<programdata>\data\top-picks`. Fixed, not a setting (F9 "Finding the Top Picks library").
- **Top Picks library:** the existing Emby library whose only folder is the Top Picks folder. Its "Latest" home-screen row is the "Latest Top Picks" row. The plugin never creates or deletes libraries.
- **Plugin data folder:** `<programdata>\data\TopPicksPlus\` (D23). Holds managed.json, plays.json, run.json, run.previous.json, state.json, `staging\` and `backups\`. Never inside any library and never under `programdata\plugins`.
- **Date added:** Emby's own record of when an item was added (DateCreated). The Latest row shows the newest date added first.
- **Run start:** the moment Run creates this run's run.json (step 1, before anything else), in UTC. **Rank time** = run start rounded down to the whole minute. Both are stored in run.json and never change, even on resume. **Rank date** of pick N = rank time minus (N − 1) hours. **The run's UK day** = the UK day of the rank time.
- **UK day:** a calendar date in the Europe/London time zone (Windows: "GMT Standard Time"). EmbyBridge passes the zone and the current time into Run and Logic; Logic never reads the clock or the zone itself.
- **Managed list:** managed.json, the plugin's record of every copy it looks after (data.md). A folder is a **managed folder** only if it is on this list.
- **Candidate:** a title that may be picked (F2 step 5).
- **Viewer-day:** one user counted as watching one title on one UK day (F6).
- **Roll-up:** turning finished UK days' plays into daily counts, deleting their user IDs, and removing counts older than 90 days (F6, D33).
- **Can be reached** (a library folder): the folder exists and listing its top level succeeds within 30 seconds.
- **Run lock:** the one lock, held in memory inside the plugin (D32). It records who holds it: `run` or `guard`. A run holds it from its start to its end; the order guard holds it for one managed entry at a time (F5, D51). Next to it is one **start waiting** flag, true while at least one start is waiting for the guard (F1) and false as soon as none is. Neither survives an Emby restart.
- **Waiting to resume (D36):** run.json exists, can be read, and its status is `running`, and no run holds the run lock. This only happens after Emby stopped during a run. Any other status (`finished`, `incomplete`, `failed`, `refused`) is never waiting, so a failed run can never block later runs.
- **Run statuses** (data.md run.json `status`):
  - `running`;
  - `finished`: every step done and nothing below made it `incomplete`;
  - `incomplete`: every step done, but at least one of: an operation was skipped with a note (F4 step 7); a pick got no copy (listed in `skipped` at step 5); a pick's copy hadn't appeared by the end of the step 8 wait. Episodes left out of a copy, drawing fallbacks, and a date or artwork refresh that didn't work are reported but don't make a run incomplete (the order guard puts dates right later);
  - `failed`: an error once run.json has been written (F4 "If something goes wrong"), a guard failing on resume at `swap` or later, or resume giving up (F5);
  - `refused`: a guard said no, or the backup failed, before anything in the Top Picks folder was changed (step 1, step 3, or a guard failing on resume at `guards` to `prepare`).
  A **successful run** is `finished` or `incomplete`. A run that ends `refused` or `failed` has `step` `done`.
- **Pending flags:** state.json's `historyLostPending` and `stateResetPending` (data.md). At step 1 and again at step 12, each one that is true is copied as true into run.json (`historyLost`, `stateReset`; never set back to false). They are **cleared only at step 12**, in state.json's write after run.json's, and only those copied as true at step 12 (under Store's state lock, so a flag set by a play event after the copy is never lost). So a refused or failed run never loses a flag: the next successful run reports it. Repeating this is harmless.
- **Stale copy:** a managed copy whose delete or update was skipped at the swap (F4 step 7). Its managed entry has `state` `stale` and no rank or rank date. Every Emby item of a stale copy (for a series: the series and **every** episode Emby has under it, including ones the plugin never recorded) gets the **stale date** `2000-01-01 00:00:00` UTC, set at F4 step 9 and kept by the order guard (D53), so it always sorts below every fresh copy, however half-updated it is. The next run's plan deletes it, or updates it if its title is picked again.
- **Text comparisons** for ordering and ties are ordinal (character by character, not by language rules); "ignoring case" means ordinal ignoring case. Paths are compared as plain full paths, ignoring case, after Logic's **path tidy**: `\\?\UNC\` becomes `\\`, a leading `\\?\` is removed, `/` becomes `\`, and a trailing `\` is removed; a path with any `.` or `..` part is never inside anything. No path is ever resolved through links (D52). **Inside** a folder means the path starts with the folder's tidied path followed by `\` (so `top-picks2` is not inside `top-picks`).
- **Single name:** a name that is not empty, is not `.` or `..`, and that SafeName's cleaning (F3, before any shortening or fallback) leaves exactly as it is and does not call reserved. So trailing dots or spaces, `:`, `~`, `\`, `/` and reserved names like `CON` are never single names. Only names **the plugin writes** must be single names (F9 check 2).
- **Found entry:** a file, folder or link the plugin finds by listing a folder (inside a managed folder, `staging\`, `backups\` or the plugin data folder), or finds already sitting at a name it is about to write, rather than one it planned. Someone else may have made it, so its name can be anything Windows allows (an Office `~$` lock file, a trailing dot or space), it can be the wrong kind (a file called `Season 1`, a folder called `Heat (1995).nfo`) and it can be read-only. Three rules, the same for Run and Store (D57):
  - **Exact path.** Every action on a found entry, and on everything below it, uses one path string: the plugin's own full path of the folder that was listed (from the paths record), then `\`, then the name exactly as the listing gave it, with `\\?\` in front (`\\?\UNC\` for a `\\server` path). So Windows can't trim a trailing dot or space and reach a different name. Listing it, reading its attributes, testing for a link, clearing ReadOnly, removing it as a link, deleting it and replacing it all use that string; whether it is a link is read from the listing's own entry or from that string, never from a normal path. The safety checks run on that same string after the path tidy: Run's F9 checks 1, 3 and 4; Store's "inside the plugin data folder, no link on the way" (F9 "Store's own deletes"). Check 2 never applies to found entries.
  - **ReadOnly.** Just before any file or folder is deleted or replaced, found or the plugin's own (a copy folder, a backup folder, a data file), its ReadOnly attribute is cleared (only that attribute). A link is never given new attributes: if removing it as a link fails (a read-only link, say), the action can't be completed (F4 step 7). Accepted at level 1: nothing makes such links by accident.
  - **Wrong kind.** A found entry at a planned name that is the other kind (a file where the plan has a folder, or a folder where it has a file) is not the planned thing: it is deleted like any other found entry before the plugin writes there (F4 step 7 "update", "Created new").
- **Removed as a link:** the link itself is deleted, by its exact path, and what it points to is never touched or entered: a folder link (junction or folder symbolic link) with a non-recursive `Directory.Delete`, a file link with `File.Delete`.
- **Created new:** every file Run or Store writes is a new file, opened with `FileMode.CreateNew`, so an existing file is never opened, written into or followed (a hard link elsewhere to an old file is never changed). If anything is already at that name, it is first removed as a found entry (a link as a link, a wrong-kind folder deleted with what is in it). A file that **replaces** another is written under a temporary name (Run: `<name>.tpp-tmp`; Store: `<name>.tmp`) and then moved over its target in one step with `File.Move(…, overwrite: true)`; just before the move the target is checked: a link is removed as a link, a folder is deleted as a wrong-kind found entry, and a file has its ReadOnly cleared. A file with nothing to replace (every file Run writes in `staging\`, which Store has just emptied, and every file in a new backup folder) is written straight to its own name. **Copying** a file (TopPicksPlus.xml into a backup, a theme video into staging) means reading its bytes and writing them into a file created new; the settings file is never parsed. `File.Replace` is never used (D57).
- **Tried once more:** a write, move or delete in the Top Picks folder, `staging\` or the plugin data folder that fails is tried once more after 2 seconds (Emby may be reading the file); if that fails too, it has failed (D57). The wait is given to Run and Store when they are built, so tests can set it to zero.

## F1 – When it runs
- Emby scheduled task **"Refresh Top Picks"**, default trigger every **Sunday at 05:00 on the server's clock**. The server is set to UK time; if the server's time zone isn't Europe/London, the run still happens and the report warns about it.
- **Run now (D35):** the settings page's Run now button asks Run directly (through EmbyBridge's API and the start-run hook). Run asks for the run lock in that same call, by the rules below: a second press while a run holds the lock is turned down at once, and one made while the first press is still waiting behind the order guard waits too and is turned down when the first takes the lock. The run then carries on in the background, and the settings page shows "run in progress" until it ends. It does not show in Scheduled Tasks. The task's own Run button in Scheduled Tasks starts the task as usual.
- **One run at a time (D32, D36).** Every way of starting a run (the task, Run now, resume, the missed-run rule) goes through one Run entry, which takes the run lock. Run now, the task and the missed-run rule are turned down if a run holds the lock or a run is waiting to resume: the settings page says "a run is already in progress", and a task start returns at once with that message in the report log. If the lock's holder is `guard`, the start sets the start-waiting flag and waits for the lock for at most 30 seconds (timed on EmbyBridge's clock): the guard sees the flag before its next entry or item, lets go and stops (F5, D51). A waiting start ends in exactly one of three ways:
  - it gets the lock and checks again exactly as if it had just arrived, before recording itself as holder `run`; while it checks, the holder still reads `guard`, so a start arriving in that moment waits too rather than being turned down. It stays in the waiting count until it records `run` or is turned down. If the check passes it records `run` and goes ahead as a run; if not it lets go and is turned down (it never held the lock as `run`, so the others keep waiting);
  - **another start takes the lock as `run` first: then every start still waiting is turned down at once** with "a run is already in progress" (so of several waiting starts only one becomes a run, however quickly that run ends, D56);
  - the 30 seconds run out: it is turned down the same way (the missed-run rule tries again at 00:15).
  The flag is false as soon as no start is waiting. **Every waiting start that is turned down first leaves the waiting count** (so the flag is false if it was the last) **and only then asks for one order-guard pass** (F5), so a guard that stopped for it always runs again once nobody is waiting. Run now's answer on the settings page comes when its wait ends (at most 30 seconds): "started" or "a run is already in progress". Only resume may take the lock while a run is waiting to resume. Emby's own task queue is not relied on; if Emby queues a second task start, it runs later as an ordinary run, which is safe (C3).
- run.json records what started each run (`trigger`: `task`, `run now`, `missed run`). Emby doesn't tell the task whether its Sunday trigger or its Run button started it, so both are `task`. A resumed run keeps its trigger and sets `resumed`.
- **Start-up order** (timers owned by EmbyBridge, each calling a Run hook). Before any timer starts, the root entry point has Store tidy its folder (leftover `*.tmp` files at its top level, removed as found entries, F9).
  1. +1 minute: roll-up (F6).
  2. +2 minutes: order guard (F5), unless a run holds the lock or a run is waiting to resume.
  3. +3 minutes: resume, if a run is waiting to resume (F5).
  4. +10 minutes: **missed-run rule** (Run's missed-run hook): if no run holds the lock, no run is waiting to resume, and state.json's last successful run is more than 7 days ago, or there has never been one (first install), start a run (`missed run`).
- Also every day at 00:05 UK time: roll-up (D33); and at 00:15 UK time: the missed-run rule again, so a week whose Sunday run was turned down, failed or refused gets a run at the next 00:15 without waiting for a restart.
- `failed` and `refused` runs don't count as successful, so the missed-run rule tries again at the next start-up or the next 00:15. A Sunday task turned down because another run holds the lock loses nothing: that other run is this week's run.

## F2 – Choosing the 10 (fully automatic)
No manual step is ever needed. Pins are optional. All of this is Logic, tested without Emby.
1. **Pins (optional) first**, in the owner's order. A pin can be any movie or series in any movie or TV library except the Top Picks library. A pin is **missing** if its source title is gone, is no longer a movie or series in a movie or TV library, or a movie's video file can't be found, or a series has no episode whose file can be found ("can be found" = EmbyBridge's source-files adapter says the file exists, D28). Missing pins are skipped and the rest move up; each is listed in the run report (with its last-known title from state.json) and marked "missing" on the settings page. Duplicates are removed when settings are saved (F8); if the settings file holds duplicates or more than 20 pins anyway (edited by hand or restored), Run keeps the first of each and the first 20. Only the first 10 usable pins are used.
2. **The remaining places go to the most watched candidates**, by **viewer-days in the 7 UK days before the run's UK day** (for a Sunday run, the previous Sunday to Saturday). Plays on the run's own day count next week. Episodes count towards their series. A pinned title isn't picked again.
3. **Order, first to last** (for watched titles; filler uses b–e):
   a. more viewer-days first;
   b. newest content first: a movie's date added; a series' newest available episode's date added;
   c. newer premiere date first; no premiere date goes after one that has it;
   d. title, A to Z, ignoring case;
   e. source Emby ID, ordinal, lowest first (so the order is always the same).
4. **Filler:** if fewer than 10 places are filled, the rest go to candidates nobody watched, ordered by 3b–3e. On the first run after install (no plays yet) every unpinned place is filler.
5. **Candidates:** movies and series in the chosen libraries (default: every movie and TV library apart from the Top Picks library). At step 1 the chosen library IDs are checked again: one that no longer exists or is no longer a movie or TV library is ignored and the report says so; if libraries were chosen and none of them is still usable, the run is refused. Logic itself drops anything in the Top Picks library or with a file under the Top Picks folder, whatever the settings say. A title appears once per Emby ID (the same film in two libraries is two titles). A movie is left out if its video file can't be found. A series is left out only if none of its episode files can be found; missing episodes are left out of its copy.
6. With fewer than 10 candidates the row is shorter. The run doesn't fail.
7. **Always 10.** The number of picks is fixed (D11).
8. **Offline drives (D25):** at F4 step 1, every folder of every chosen library, and of every pinned title's library, must be reachable (EmbyBridge's source-files adapter, D28). If any can't, the run is **refused** and the report names the folder.

## F3 – What each copy contains
**One naming rule for every folder and file the plugin makes** (Logic, `SafeName`):
- **Cleaning:** remove `< > : " / \ | ? * ~` and control characters (`~` so no name can look like a Windows short name), turn runs of spaces into one space, then trim leading spaces and trailing dots and spaces.
- If the result is empty, or a name Windows reserves (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, any case, with or without an extension), use the fallback given (always the item's Emby ID).
- Shorten to the length limit at a whole character, then trim again.
- **Lengths:** copy folder name at most 60 characters; episode file name (before the extension and language parts) at most 80. Every full path, including the 8-character temporary suffix `.tpp-tmp` (F4 step 7), must be at most 240 characters both in the Top Picks folder and in `staging\` (Logic checks the longer of the two). If a path is too long, the episode title part is shortened; if it still can't fit, that episode is left out and the report says so.
- Names are compared ignoring case when checking for clashes, as Windows does.

**Names:**
- **Copy folder:** `Title (Year)`, or `Title` with no year; fallback the source ID. If two picks get the same name, or the name is already used (ignoring case) by anything in the Top Picks folder, folder, file or link (managed or not, including a managed folder being deleted this run), the name is cut to 55 characters and ` - 2`, ` - 3` … added until free. The plugin never writes into a folder that isn't managed.
- **A title that stays keeps its folder name** for as long as it stays, even if its title or year changes, so Emby keeps the same item. A new name is only used when a title comes back after dropping out.
- **Movie files:** `<folder>.strm` and `<folder>.nfo`. The .strm points to the movie's main video file (for a movie with several versions, the one Emby plays by default).
- **Series:** `tvshow.nfo` in the copy folder, then one folder per season: `Season 1`, `Season 2` … (`Specials` for season 0). Episode files are `<Series> - S01E02 - <Episode title>` (`.strm` and `.nfo`), where `<Series>` is SafeName of the source series' name cut to 40 characters, and numbers are padded to at least 2 digits. With no episode title: `<Series> - S01E02`. A video file holding several episodes gets one .strm named with its first and last, `S01E01-E02`, and its managed entry lists every episode it holds. An episode with no season or episode number goes in `Specials` as `<Series> - S00E<Emby ID>`.
- **Subtitles:** for movies and episodes, external subtitle files (.srt, .ass, .ssa, .vtt, .sub) next to the source video are copied (read through the source-files adapter, D28), keeping the source's language and forced/default parts: `<copy file name>.en.forced.srt`.
- **The .strm content** is exactly the source file's full path and nothing else. If the path contains a line break (CR or LF), that item is left out and reported.

**.nfo files** are built as text by Logic with an XML writer (any text from Emby is escaped, never pasted in raw; characters XML doesn't allow at all are removed first), UTF-8, and written by Run:
- Movie: `title`, `originaltitle`, `year`, `premiered` (yyyy-MM-dd), `plot`, `mpaa` (age rating), `genre` (one per genre), `runtime` (minutes), `uniqueid` (each provider ID, e.g. imdb, tmdb), `dateadded`.
- Series (`tvshow.nfo`): `title`, `originaltitle`, `year`, `premiered`, `plot`, `mpaa`, `genre`, `uniqueid`, `dateadded`.
- Episode: `title`, `showtitle`, `season`, `episode`, `aired`, `plot`, `runtime`, `mpaa`, `uniqueid` (each provider ID the source episode has; for a multi-episode file, those of its first episode), `dateadded`.
- The `uniqueid` lines are what make Emby share watched state between a copy and its real title (D39, D43, F7). They are always written when the source has them.
- **Never in an .nfo:** `watched`, `playcount`, `lastplayed`, `resume` or any other per-user element, so a copy's .nfo can never set anyone's watched state (C35).
- `dateadded` is the rank date in **UTC**, `yyyy-MM-dd HH:mm:ss`, so the autumn clock change can't make two ranks share a time. Every episode of a series gets the series' rank date. The plugin also sets the date itself at F4 step 9; if Emby ever re-reads the .nfo as local time, every copy moves by the same amount, so the order still holds, and the order guard puts the exact values back.

**Artwork** (images come from EmbyBridge as bytes; Artwork never touches files):
- `fanart.jpg`, or `fanart.png` if the source backdrop is a PNG: the source's first backdrop, as-is.
- `logo.png`: the source logo, if there is one.
- `backdrops\theme.mp4`: the source theme video, if there is one, copied (opened through the source-files adapter) only when a copy is first created. An update keeps it as it is.
- `folder.png` and `thumb.png` (the same picture), drawn at **1000×562** (D6) with the embedded font **Montserrat ExtraBold** (SIL OFL, D15):
  - Background: the backdrop scaled to cover the whole picture, centred. No backdrop: the poster, scaled to the full height and centred on dark grey `#111111`. Neither: plain `#111111`.
  - A dark fade over the left 45%: 70% black at the left edge to clear at 45%.
  - The rank number in white. The font size is chosen so the digit "0" is 390 px tall (measured from the drawn glyph), the number starts 40 px from the left edge and is centred top to bottom. If the number is wider than 360 px ("10"), it is scaled down to 360 px wide, so it never reaches the logo box.
  - The logo fitted inside the box x 420–960, y 60–300, keeping its shape, centred in the box. No logo: the title in white in the same box, at most 2 lines, as large as fits between 72 px and 36 px, then cut with "…".
  - **If drawing fails** (an image that can't be read, or SkiaSharp can't load; Artwork catches any `Exception` around its drawing calls): the copy's `folder` and `thumb` pictures are the source backdrop (or, with no backdrop, the poster) saved as-is with their own extension (`folder.jpg` / `thumb.jpg` for a JPEG). With neither image, there is no folder picture. The report says drawing failed for that title.
  - Whatever is written, the copy ends up with only one `folder.*` and one `thumb.*`: an old one with another extension is removed (F4 step 7 "update").

## F4 – Each week's update, in order
Run carries out these steps. run.json's `step` names the step in progress (the value is given in brackets after each step's name), so a restart can carry on (F5). A run that refuses changes nothing in the Top Picks folder.
1. **Create the run and refuse or go** (`guards`): Store copies the previous run.json to run.previous.json (by reading it and writing run.previous.json as a normal atomic write, created new, never a file copy over the old one) **only if that run was successful** (so run.previous.json always holds the last successful run before this one, and failed or refused runs never hide it). Then it writes the new run.json with every field set (data.md gives each field's starting value): new `runId`, `startedUtc` (run start), `rankTimeUtc`, `trigger`, `resumed` false, `resumeCount` 0, `step` `guards`, status `running`, `timeZoneWarning` (true if the server's time zone, passed in by EmbyBridge, isn't Europe/London), `pluginVersion` and `embyVersion`, every list empty, every other true/false false, `rowCheck.result` `not run`. Then the pending flags are carried over (see "Pending flags"). Then the guards, in order: old-plugin guard, finding the Top Picks library (F9), managed.json damaged, or missing while the Top Picks folder holds a copy-looking folder (F9), chosen libraries still usable (F2 step 5), offline-drive check (F2 step 8). If any fails, status `refused`, `step` `done`, the report says why, and nothing else is changed; the lock is released and the order guard runs once (F5). **If run.json can't be written** (or copying run.previous.json fails before it), there is no run to record: the error is logged (where and the error type), the lock is released (then the order guard runs once, F5), and Run now's answer, or the task's report log line, says "the run could not start". (A resumed run does not create run.json again: F5.)
2. **Roll-up** (`rollup`) the play log (F6). Safe to repeat.
3. **Back up** (`backup`, F9) into `backups\YYYY-MM-DD-HHMMZ\` (the run start, UTC). If a **complete** folder of that name is already there (a resumed run, or two runs in the same minute), it is kept and the backup is skipped; an **unfinished** one (no `complete` file) is deleted and made again from scratch, never written into; anything else of that name (a file, or a link) is removed as a found entry and the folder made. If the backup fails, the run is refused (nothing has been changed yet).
4. **Choose** (`choose`) the 10 (F2).
5. **Plan** (`plan`): first tidy leftovers in managed.json: an `incoming` entry whose folder is in the Top Picks folder **and whose `staging\` folder is gone** becomes `active` (a folder move is one rename, so the plugin moved it); any other `incoming` entry is removed, leaving its folder alone; an `active` or `stale` entry whose folder isn't there is removed (if that title is picked again, it is planned as an add with a fresh folder). A `stale` entry whose folder is there stays `stale` and is planned like any other copy: `update` if its title is picked, otherwise `delete`. Then compare the 10 with the managed list and write, in one write of run.json, `picks`, `missingPins`, `ignoredLibraries`, `skipped` and every operation, before anything is changed: `delete` a drop-out, `update` a stayer, `add` a new title. Each `update` and `add` holds the **full planned managed entry** (folder, source, kind, rank, rank date and the file list with each .strm's source items), so the swap and a resumed swap never need to work it out again. A pick whose copy can't be planned at all (for example its every episode was left out) gets no operation and is listed in `skipped`.
6. **Prepare** (`prepare`): Store empties `staging\`. Run writes every new title's whole copy, and every stayer's whole new set of files (everything except `backdrops\theme.mp4`), into `staging\<copy folder name>\` with the same layout it will have in the Top Picks folder, every file created new ("Words used here"). Emby never sees `staging\`.
7. **Swap** (`swap`), one operation at a time, in the order **deletes, then updates, then adds**, each marked done in run.json when it finishes. **Before an operation's first change**, the F9 checks are run on the operation's own copy folder (and, for an update or add, on its staging folder, which is also listed: a link anywhere inside it fails, F9 check 4); if any fails, the whole operation is skipped and nothing of it is changed. An **update** whose copy folder or staging folder is missing is skipped the same way (its entry becomes `stale`; if its folder is gone, the next plan removes the entry). A managed copy folder that has itself become a link is removed as a link (never entered) and the operation then goes on as for a missing folder (a delete just removes its entry). For an add, these checks run just after its `incoming` entry is written (which changes nothing in the Top Picks folder), so its folder is already on the managed list; if they fail, that entry is removed again. Links **inside** a copy folder never skip its delete or update: they are removed as links (F9 check 4).
   - **Write order for every operation:** managed.json is changed first, then run.json marks the operation `done` (with its `note` if it was skipped). A stop between the two repeats the operation on resume, which each operation below allows.
   - **delete:** if its folder is still there, delete it through the delete guard (F9): list it one level at a time, remove links as links, delete every found entry (exact path, ReadOnly cleared first, "Words used here"), then the folder itself; then remove its entry.
   - **update:** the same folder is kept. First the **clear-out**, before anything is written: the folder is listed one level at a time (exact paths, "Words used here"); every link inside it (file or folder, at any depth) is removed as a link, never entered; every found entry that is not in the **new set as the same kind** is deleted (ReadOnly cleared first); then any folder left empty is removed. The new set is the planned files and the folders on the way to them, compared ignoring case as Windows does (so `Heat (1995).NFO` is the same file as `Heat (1995).nfo`), plus `backdrops\theme.mp4` and its `backdrops` folder; a real file kept must be planned as a file, and a real folder kept must be planned as a folder. So a leftover `.tpp-tmp`, an episode that has gone, an old `folder.jpg` next to a new `folder.png`, an Office `~$` file, a file called `Season 1` and a folder called `Heat (1995).nfo` are all gone before the first write. Then each file from staging is written into the folder as a replacing write, created new ("Words used here": under `<name>.tpp-tmp`, then moved over the old file, or into place if there is none). (A link in the staging folder already skipped the update before its first change, F9 check 4.) So the folder ends up exactly matching the new copy. Then the entry is replaced by the operation's planned entry, keeping the copy item IDs already found (the copy's `itemId`, and each file's `itemId` where its path is unchanged); `state` is `active` (so a `stale` copy whose title is picked again and updated is `active` once more).
   - **add:** if anything of the target folder's name (a folder, file or link) already exists in the Top Picks folder while its staging folder is still there, the add is skipped (see below) and **no entry is written**; if an `incoming` entry for it was already written (a resumed run), that entry is removed, so the plan's tidy can never adopt a folder the plugin didn't make. Otherwise write the operation's planned entry (stored with `state` `active`) to managed.json with `state` `incoming` (if it isn't there already; from then on the target folder is on the managed list, F9 check 1), move its folder from `staging\` into the Top Picks folder (a move within the same drive, since both are under programdata; a folder move is a single rename), then mark the entry `active`. So a folder in the Top Picks folder is never unknown to the managed list. If the folder is already in the Top Picks folder and gone from staging (a resumed run), it was already moved: just mark the entry `active`.
   - Any operation that can't be completed (a check fails, the target of an add already exists while its staging folder is still there, a file can't be written or deleted) is skipped: it is marked `done` with a `note` in run.json (so resume never tries it again), and the run will end `incomplete`. **A skipped delete or update** leaves its copy in place, possibly half updated: its managed entry becomes `stale` (rank and rank date cleared, item IDs kept; for an update its `files` list becomes every .strm in the old entry or the planned one, one entry per path, so plays on any of them still match, F6; for a path in both, the planned `sourceItemIds` and the old `itemId` are kept), it gets the stale date (step 9, F5), and the next run deletes or updates it (step 5). A skipped update's pick is listed in `skipped` ("copy not updated"), in the same run.json write that marks the operation `done`, and counts as having no copy (step 11). A skipped add writes nothing to managed.json.
8. **Rescan** (`rescan`) only the Top Picks library, and wait until every `active` copy is in the library (stale copies are not waited for): for a movie, its copy item; for a series, the copy series and a copy episode for every .strm in its managed entry. Up to 15 minutes, or 30 minutes if any series' managed entry lists more than 200 .strm files. Each copy item's Emby ID is stored in managed.json as it is found.
9. **Set the order** (`dates`): for every `active` copy item that has appeared, set its date added to its rank date; for every `stale` copy, set every one of its items Emby has (found as for the order guard, F5) to the stale date. Both use Logic's **target date** rule (rank date for `active`, stale date for `stale`) (for a series, the series and every episode; if the first build chunk shows Emby orders series in Latest by "date last media added", that is set too, C34). The same date is already in the .nfo (card 0001). Before any change, EmbyBridge checks that the item's path is inside the Top Picks folder (Logic's path check), and refuses the change if not (F9). **The plugin never changes anyone's watched state or resume point** (D39, F7).
10. **Refresh artwork** (`artwork`) for each `active` copy that has appeared, so the number on the picture matches. The refresh asks Emby for images only (no metadata refresh, nothing saved back to the .nfo; C34 confirms). Then read each date added back and set it again if the refresh changed it.
11. **Check the row** (`check`, D22): ask Emby for the Latest Top Picks row as the apps do (the "latest items" request for the Top Picks library, 10 items, grouped by series), as the **check user**: the first user, by user ID (ordinal), who isn't an administrator, isn't disabled and can see the Top Picks library; if there is none, the first administrator the same way, and the report says so. EmbyBridge gives the users as plain records (ID, administrator, disabled, can see the Top Picks library); Logic picks the check user. The request does not leave out items the check user has watched, so a pick they have watched still counts (the first EmbyBridge chunk confirms the request; C34).
    - **Expected** = the picks whose copy is `active`, that the check user is allowed to see, in rank order. **Allowed to see** = EmbyBridge's "which of these copy items can this user see" action says yes (Emby's own access check for that user: library access and parental controls; a copy item not found yet counts as allowed). Every pick not in the returned row is listed in `leftOut` with why: `parental controls` (not allowed to see it), `no copy` (skipped), or `not in row` (expected but not returned, for example because it hadn't appeared yet).
    - Each returned item is matched to the managed list by its Emby ID (the copy's `itemId`, or a file's `itemId`), and if that finds nothing, by its path being inside a managed folder (Logic's path rule). An episode (Emby sometimes returns one instead of its series) counts as the copy whose folder holds it, so a new episode of a stale series counts as that stale copy. An item that matches no managed copy is reported by name and makes the check fail. An item that matches a `stale` copy is reported as stale.
    - **passed** = the returned titles, in order, are exactly the expected picks, and no pick was left out for `no copy` (so no picks and an empty row passes). **partial** = the returned items that are not stale are some of the expected picks in rank order, every stale copy returned comes after them, and the row is not a pass (a pick missing, or a stale copy shown). **failed** = anything else: expected picks out of order, an unmatched item, or a stale copy before an expected pick. A missing pick or a stale copy after the picks is never `failed` (C39). **not run** = the run stopped before this step. (A late copy that appears by step 11 is in the row in its place, so it passes.)
12. **Record** (`done`): first run.json, in one write: status `finished` (or `incomplete`, as defined in "Words used here"), `finishedUtc`, `step` = `done`, with the pending flags copied in again (so damage found during this run shows in this run's report). Then Run makes one `IStore` call that updates state.json in one write under the state lock: `lastSuccessfulRunUtc` (= run.json's `finishedUtc`), each pin's last-known title, and **only the flags that were copied into run.json as true** set to false (the only place they are cleared; a flag set after the copy stays true for the next run). Release the lock. Run the order guard once. (If Emby stops before the run.json write, resume repeats from step 8, which is harmless. If it stops between the two writes, the run is already recorded as successful; state.json just keeps the older date and the flags, so the missed-run rule may start one extra run and the next report may repeat a warning, both harmless. An **error** after the run.json write (the state.json write fails) is the same case: it is only logged, the run stays as recorded, the lock is released and the order guard runs once; it never turns a recorded run `failed`.)

**If the step 8 wait runs out:** steps 9–11 run for every copy that has appeared, the status is `incomplete`, and the order guard (F5) sets the dates of the rest when they appear. Copies that appear late already carry the right number on their folder.png.

**If something goes wrong** (an error, not a restart) at any point once run.json has been written, including inside step 1's guards: the run stops, the status is `failed`, `step` = `done`, and the report says which step and what failed in plain words; before step 7 it adds "nothing in the Top Picks folder was changed". No operation is undone. The lock is released, then the order guard runs once (F5). If even writing `failed` to run.json fails, the lock is still released and the error logged; run.json then still says `running`, so it counts as waiting to resume and other starts are turned down until Emby next restarts, when resume picks it up (F5). Accepted: it needs a disk error twice in one run. The order guard keeps the row ordered for the copies in place. The next run starts fresh (step 5 tidies leftovers).

**Errors never reach Emby:** every hook, timer, event handler and API action catches every error. In a run, an error makes the run `failed` as above; anywhere else it is logged and that one action is dropped. **What an error log line holds:** where it happened (hook, step) and the error's type name only, never its message or stack, wherever the action concerns a user (plays, the start list, user data, step 11's list of users and the check user, the "which copy items can this user see" action, and the administrator check); elsewhere the message may be logged at Debug, and never a user ID, user name or (on the play paths) a title (F6).

## F5 – Order guard and resume
- **Order guard (D51):** runs 2 minutes after Emby starts, once after every start that ends (finished, incomplete, refused, failed, gave up, or "could not start": Run releases the lock, then runs the guard once), and 2 minutes after the last Emby library change to a Top Picks item (item added or updated in the Top Picks library: EmbyBridge waits for 2 quiet minutes, so a full scan triggers it once at the end), and once for every waiting start that is turned down (F1). Its own date changes may start it again 2 minutes later; that pass finds nothing to change, so it changes nothing and starts nothing (no self-change filter, D56). **One pass at a time:** a trigger that comes while a pass is running is remembered as **one more pass** when this one ends (several such triggers still mean one more pass), so no trigger is lost when a pass stops early. It works **one managed entry at a time**: for each entry it takes the run lock (holder `guard`) only if it is free, reads managed.json afresh, checks that one entry, and releases the lock. Before each entry, and before each item date it sets, it looks at the start-waiting flag. If a run holds the lock or is waiting to resume, a start is waiting, or managed.json is damaged or missing, it **stops** (a run always ends by running the guard again). So a run start only ever waits for one item's date change (F1). For each `active` and `stale` entry it compares the date added of the copy's items (the series and each episode, and the series' "date last media added" if C34 showed Latest uses it) with Logic's target date (rank date, or the stale date) and sets any that differ by more than 1 second. It finds a copy's items by the IDs in managed.json; an ID that is null or no longer exists is looked up by path (folder or .strm path) and stored. For a `stale` series it asks Emby for every episode under the copy series, not only those in `files`. If nothing is found, that copy is skipped until next time. `incoming` entries are ignored. It only sets dates: it never refreshes artwork, changes files or touches watched state. It releases the lock however it ends. The exact Emby events are confirmed in the first EmbyBridge build chunk (C4, C32).
- **Resume (D36):** at +3 minutes after start-up, if a run is waiting to resume, Run takes the run lock (the one start allowed while a run is waiting), sets run.json `resumed` true and adds 1 to `resumeCount`. If `resumeCount` is now 3 (Emby stopped during the same run three times: the first two stops were resumed, this is the third), the run is not tried again: status `failed`, `step` `done`, message "gave up after 3 restarts", lock released, then the order guard runs once. Otherwise, by run.json `step`:
  - `guards` to `plan`: carry on from step 1's guards **without creating run.json again**: every field already in run.json is kept (`runId`, run start, rank time, `trigger`, `resumeCount`, `historyLost`, `stateReset`), run.previous.json is not touched, and the pending flags are carried over again (harmless, they only add). Steps 2–5 then run as normal; step 5 replaces `picks`, `missingPins`, `ignoredLibraries`, `skipped` and `operations` in one write. Each of these steps is safe to repeat: guards only read; roll-up repeats harmlessly; the backup follows step 3's rule (skipped if this minute's folder is complete, otherwise made again). If a guard now refuses, the status is `refused`.
  - `prepare`: run the guards again (a guard that fails makes the status `refused`, since nothing in the Top Picks folder has been changed), then Store empties staging and step 6 starts again.
  - `swap`: run the guards again, then carry on from the first operation not marked done, using the planned entries in run.json and the files already in staging. Repeating is safe: a delete whose folder has gone just removes its entry; an update's files are written again; an add follows the add rules in F4 step 7. If an operation can't be finished (its staging folder is missing and the target isn't there), it is skipped with a note as F4 step 7 says (an update's entry becomes `stale`; an add's `incoming` entry is removed), and the run ends `incomplete`.
  - `rescan`, `dates`, `artwork`, `check`: run the guards again, then start again from step 8 (each is safe to repeat).
  - A guard that fails on resume at `swap` or later makes the status `failed` with the guard's message.
  - Any error during resume is handled as any other run error (F4): status `failed`, lock released. So a run can never stay waiting to resume after its resume has been tried.
- What the row may show while a run is in progress: for a few minutes, a mix of last week's and this week's titles. When the run finishes, the row is complete and in order.

## F6 – Counting plays
- EmbyBridge listens for Emby's "playback started", "playback stopped" and "user data changed" events and passes them to Run's record-play hook. It ignores trailers, extras and anything that isn't a movie or an episode.
- **Which title it counts for:** a play on a copy item counts for the source title. The copy is found in the managed list by its path (each managed .strm lists the source items it holds, data.md). If managed.json is damaged or missing, a play on a copy can't be matched and is dropped (logged at Debug without user or title). A play on a `stale` copy still counts for its source. A play on a source item counts for its movie or series, wherever it was started.
- **Runtime** of what was watched is always the **source** item's runtime (for a copy, the first source item its .strm holds), never the copy's.
- **Minutes watched in a sitting** = the stop position minus the start position (from the matching "playback started", held in memory only, by Run), in whole minutes rounded down, never below 0 or above the runtime. If the start wasn't seen (for example Emby restarted), the stop position is used. The in-memory start list holds at most 1,000 entries; entries older than 24 hours, and the oldest when it is full, are dropped.
- **Finished** = the item **became played during this playback**: at the matching "playback started" it was not played for that user, and at "playback stopped" Emby reports it played (Emby does this itself when playback passes its own "played" point). The played state at start is held in the in-memory start list. Replaying something already watched is never "finished"; it counts only by minutes. If the start wasn't seen, `finished` is false.
- **Marked by hand** = a "user data changed" event whose reason is Emby's "played toggled" (not a playback save) and which sets a movie or episode (source or copy) to played. It adds a sitting with 0 minutes and `markedPlayed` true, on the UK day it happened. Clearing played state adds nothing and removes nothing already recorded. Because a copy and its real title share watched state (D39, D43), Emby may report one mark on both; both count for the same title and day, so that user still counts once. The first EmbyBridge build chunk confirms Emby's reason value (C34).
- **Which users count:** every Emby user, administrators included.
- **What counts as watched:** a user counts for a title on a UK day if, that day, they finished an item in it or marked one played by hand, or their minutes on the title that day add up to at least 50% of the runtime, or 20 minutes when the runtime isn't known. For a series, the runtime is that of the episode watched, and each episode is judged on its own: one qualifying episode is enough. Two sittings of the same film at 30% each count. A sitting belongs to the UK day on which it stopped.
- **No viewing history (D21, D33):** who watched what is held only in plays.json's `today` section, so each person is counted once a day. **Roll-up** happens 1 minute after start-up, at 00:05 UK time every day, and at F4 step 2: every `today` entry from a UK day before the current one is turned into "title, day, number of viewers", and those entries (with their user IDs) are deleted, in one atomic write. A day is rolled up once: its entries are deleted in the same write that adds its counts. Daily counts more than 90 days before the current UK day are removed at every roll-up. Store keeps one lock around every change to plays.json, so the listener and a run never overwrite each other.
- Plays seen before start-up has finished wiring the plugin are dropped (logged at Debug without user or title).
- **Logging:** plays are never logged at Info level. The plugin never puts a user ID or user name into any log line or error message, and lines on the play paths (listeners, the start list, roll-up) never name a title either, even at Debug, since a title and a time together can show who watched what. Errors on these paths log only where and the error type (F4).

## F7 – Watched status (D39)
- **A copy and its real title share watched state.** Each copy's .nfo files carry the source's provider IDs (`uniqueid`, F3), and Emby itself shares watched ticks and resume points between items with the same provider IDs, as it does with the old plugin today (owner's proof tests, D39, D43, D49). So finishing a film from the row marks the real film watched, and a half-watched film can be resumed from the row or from the real title.
- **The plugin never changes anyone's watched state or resume point**, on a copy or on a real title. No part has a way to do it (F9).
- **Known limitations, accepted by the owner:** a user who has "hide watched from Latest" turned on may see fewer than 10 titles in the row once they have watched some picks (D39). Copies appear in search next to the real titles, as they do today.
- Episodes carry their own provider IDs too (F3, D42) and share watched state both ways (D43). Deleting a copy, film or series, every week and at install, leaves the real titles' watched ticks and resume points as they were (D43 for films, D49 for a series' episodes). C14 stays the release check that this still holds.
- **Emby's own savers stay off for the Top Picks library (D50):** "Save metadata as .nfo" (Nfo saver), "Save user watch data" and "Save artwork into media folders" are off (owner turned them off 2026-11-08), so Emby never rewrites a copy's .nfo or artwork. The install steps check this (releases.md) and C34 confirms setting dates and refreshing artwork leaves the .nfo alone.

## F8 – Settings page and run report (Dashboard → Plugins → Top Picks Plus)
- **Administrators only.** Every action of the plugin's API (save settings, pin search, check pins, Run now, run status, read the report) first takes the signed-in user from Emby's own authorisation of the request, never from a user ID in the request, and refuses anyone who isn't an Emby administrator with "Administrators only" and no data. This check comes before anything else, even before "starting up" (Logic's admin rule, C70). Hiding the page is not relied on. Every route also carries Emby's own `[Authenticated(Roles = "Admin")]` attribute, so Emby turns away a missing, signed-out or non-administrator token before the plugin's code runs; the plugin's own check stays as the second line (C26, C70). Actions that change something (save settings, Run now) accept only POST requests; the rest only GET.
- **Libraries** to choose from (movie and TV libraries only). The Top Picks library is never offered.
- **Pins:** search for a movie or series, add it, drag to reorder, remove. When the page opens it asks the API's **check pins** action which pins are missing now (the F2 step 1 rule, live), and marks them "missing"; the report shows which were missing at the last run.
- **Saving checks every value** (EmbyBridge's API, on the server, using Logic's save rules with the facts EmbyBridge looked up): library and pin IDs must be Emby IDs that exist and are a movie or TV library, or a movie or series in one; the Top Picks library and its items are refused; duplicate pins are removed; at most 20 pins. A bad value is refused with a plain message and nothing is saved. Good values are saved through Emby's plugin configuration (the Settings part's configuration class). A settings file changed outside the page is checked again by Run (F2 steps 1 and 5).
- **Run now** button (F1, D35), plus a status line read from the run-status API: "run in progress", "waiting to resume after a restart", or the last run's status. While a run is in progress or waiting to resume, the page shows that status and, below it, the last successful run's report (run.previous.json), not the half-written current one.
- **Last run report:** plugin version and Emby version; what started it and whether it was resumed; when it ran; status (finished / incomplete / failed / refused) and a plain-words message; each pick with rank, title, why it was picked (pinned / N viewer-days / filler) and whether its copy, date, artwork drawing and artwork refresh worked; skipped items and why; missing pins; ignored libraries; the row check result (passed / partial / failed / not run, which kind of user was used, what was left out of the expected list and why, and exactly what Emby returned if it didn't pass); total viewer-days in the 7-day window; whether popularity history was lost (damaged plays.json) or run state was reset (damaged state.json); a time-zone warning if needed. If the last run was `refused` or `failed`, the page also shows the last successful run (run.previous.json). No user names or IDs appear anywhere.
- **Text from Emby** (titles, names, messages) is put on the page as plain text only, never as HTML.

## F9 – Safety
- **Finding the Top Picks library (D52):** the Top Picks folder is `<programdata>\data\top-picks`. The run is refused if no library has it as a folder, if more than one does, if the library holding it has any other folder, if the Top Picks folder or the plugin data folder is itself a junction or symbolic link, or if the Top Picks folder is inside, or contains, any other library's folder, or the plugin data folder, or if any library's folder is inside, or contains, the plugin data folder (so no library can show `staging\`). All of these compare plain tidied paths, ignoring case (spec "Words used here"); nothing is resolved and no other library's folder is opened, so an offline drive in a library you didn't choose can't slow or stop this check. **Who does what:** EmbyBridge gives the libraries and their folder paths as Emby holds them. Run checks the Top Picks folder isn't itself a link, and Store checks the plugin data folder isn't (through `IStore`), both by its reparse-point attribute (`FileAttributes.ReparsePoint`). Logic makes every comparison. A link hidden somewhere above these folders (outside the plugin's control) isn't looked for: the plugin only ever deletes inside its own managed folders, never through a link (check 4), so it can still never reach real media.
- **Before every write, move, delete or replace** in the Top Picks folder or `staging\`, Run checks (and skips and reports the item, or the whole operation at the swap, F4 step 7, if any check fails):
  1. the target folder is on the managed list (for a file: it is inside a managed folder; an add's folder is on the list once its `incoming` entry is written, F4 step 7), or is inside `staging\`;
  2. **names the plugin writes** are single names ("Words used here"): a copy folder's name, and each part of every file path the plugin plans (the plan's entry, and the files it writes in staging). Found entries (handled by their exact path, "Words used here") are not checked against this rule, so a file someone else put inside a copy folder can never block its delete or update;
  3. its full path is directly inside the Top Picks folder (for files: inside the managed folder), or inside `staging\`;
  4. **on the way:** `staging\` itself, every folder between the Top Picks folder (or `staging\`) and the target, and the target folder itself, is not a junction or symbolic link (reparse-point attribute); a link there fails the check (except a managed copy folder that is itself a link, which is removed as a link, F4 step 7). This check is made before the operation's first change **and again just before each write, rename, delete, folder listing and the add's move** (a cheap attribute read each time); the split-second left between the check and the action is accepted (level 1). A part that doesn't exist yet (an add's target before its move, a resumed delete or add whose folder has gone) is not a link and passes; what the operation then does with a missing folder is in F4 step 7 and F5. **Inside:** while deleting or updating, the plugin lists the folder itself, one level at a time, and anything inside that is a link (file or folder) is removed as a link and never entered; this is part of the operation, not a failure. An update does this for its whole folder before its first write (F4 step 7, clear-out), and checks each file it replaces again just before replacing it. Before an update's or add's first change its **staging folder** is listed the same way, and a link anywhere in it skips the whole operation (Run made every file in staging, so a link there means something is wrong). With no link on the way, and the Top Picks folder and plugin data folder checked as above, the full path is the real location.
  **In practice:** the plugin deletes only folders on the managed list (`active` or `stale`) and the files inside them. If someone puts their own file inside a managed folder, it goes when that folder is deleted or updated (the one exception to "deletes only what it made"). Unmanaged folders and loose files in the Top Picks folder are never touched. `staging\` can never be on the managed list (managed names are folders directly in the Top Picks folder).
- **Emby items the plugin changes:** only date added (and "date last media added" if C34 needs it) and artwork refresh, and only on items whose path is inside the Top Picks folder. EmbyBridge checks each item with Logic's path rule before every change and refuses if not: "inside the Top Picks folder" comparing the item's full path, as Emby gives it, with the Top Picks folder from the paths record (the same one string everywhere: play matching, the order guard's look-ups, these checks), as tidied paths ignoring case; no file access is needed. EmbyBridge has no action that changes played state or resume points on any item (D39).
- **Store's own deletes** (emptying `staging\`, pruning `backups\`, removing old damaged run.json and state.json files, deleting a damaged plays.json, removing leftover `*.tmp` files at the top level of the plugin data folder at start-up) are only ever inside the plugin data folder, with the same full-path and no-link checks: no link on the way to `staging\`, `backups\` or a file being deleted (if `staging\` or `backups\` itself is a link, or a file, Store removes it, as a link or as a wrong-kind found entry, and makes a real empty folder in its place), a backup folder that is itself a link is removed as a link, a link inside `staging\` or a backup folder is removed as a link, never entered, every other found entry is deleted (exact path, ReadOnly cleared first, "Words used here"), and backups are only pruned by their own name pattern (`YYYY-MM-DD-HHMMZ`) (C76). Every file Store writes is created new ("Words used here").
- **Old-plugin guard:** if Emby has loaded a plugin whose assembly is `Emby.TopPicks`, every run is refused and the report says to uninstall it first. Nothing else is matched by name.
- **Damaged files (D37).** A file is **damaged** if it can be read but its contents can't be parsed as JSON, it has a `schemaVersion` the plugin doesn't know, or any field breaks data.md's rules (wrong type, value out of range, missing required field, a folder name that isn't a single name, a path that leaves its folder). A file that can't be **opened or read at all** (locked by another program such as antivirus, a disk error) is **not** damaged: it is left alone, and the action that needed it fails as an error (a run ends `failed`; a play or roll-up is dropped and logged, and the roll-up tries again next time). A missing file is not damaged either (data.md says what each missing file means).
  - **managed.json** damaged: left exactly where it is and every run is refused until it is fixed. A **missing** managed.json while the Top Picks folder holds a copy-looking folder is treated the same way (Store reports the file missing; Run looks for copy-looking folders, since only Run reads the Top Picks folder). The report gives the fix, which is the same as installing: stop Emby, empty the top-picks folder (keeping any folder you made yourself), delete managed.json, start Emby, Run now. The order guard and play matching on copies do nothing while it is damaged or missing (F5, F6).
  - **state.json** damaged: renamed to `state.json.damaged-YYYYMMDD-HHMMZ` and replaced by an empty one with `stateResetPending` true; the run carries on and the report says run state was reset (the missed-run rule may start an extra run, and missing pins show no title until the next run). The newest 3 such files are kept. It holds no user IDs.
  - **run.json** damaged: renamed to `run.json.damaged-YYYYMMDD-HHMMZ`; there is nothing to resume, and a fresh run can start. The newest 3 such files are kept. It holds no user IDs. (run.previous.json damaged: it is ignored and overwritten at the next successful run's step 1.)
  - **plays.json** damaged: **deleted at once**, because it may hold user IDs and can't be read to roll them up; counting starts again from empty, `historyLostPending` is set, and the report (of this run if a run is in progress, otherwise the next) says the popularity history was lost. The daily counts can be put back by hand from the newest backup (stop Emby, copy its plays.json over, start Emby); backups never hold user IDs and load as a normal plays.json (C63).
  - A damaged-file name already taken (two in the same minute) gets `-2`, `-3` … at the very end (`state.json.damaged-20261115-0500Z-2`), so no damaged file is ever written over. Keeping "the newest 3" counts these too, newest by the time in the name, then the higher number.
  - **A data file that is itself a link, or a folder,** is never read: it is removed (as a link, or as a wrong-kind found entry with what is in it) and counts as missing (data.md); for plays.json `historyLostPending` is set, for state.json `stateResetPending` is set, so the report says so (C76). So nothing someone puts at a data file's name can stop every run starting.
  - Damage is noticed whenever Store reads the file (a run, a roll-up, a play, the order guard), and handled the same way each time.
- **Backups:** at F4 step 3, plays.json **with its `today` section emptied** (`"today": []`, so no user IDs and still a valid plays.json) and `TopPicksPlus.xml` (copied as bytes into a file created new, never parsed) are copied into `backups\YYYY-MM-DD-HHMMZ\`, then an empty `complete` file is written last; a folder without `complete` is unfinished and is not counted. Files that don't exist yet are skipped. The 8 newest complete folders are kept; an unfinished folder older than the newest complete one is deleted at pruning. To restore popularity counts or settings: stop Emby, copy the file back over the live one, start Emby (C63 tries both). managed.json and state.json are not backed up: neither can be usefully restored (D37).
- **Personal data:** none is kept (D21, D33). Today's not-yet-counted plays hold user IDs until the next roll-up after their day ends. Nothing is sent anywhere; the plugin makes no network calls (no part may use `System.Net`).
- **Age ratings:** each copy's .nfo carries the source title's age rating, so Emby's parental controls apply to copies as to the originals.

## F10 – Staying working through Emby updates
- The build targets a fixed Emby plugin SDK version (D14).
- After every Emby server upgrade, the owner runs check C20. The plugin writes its version and the Emby version at the top of each run report.

## How the parts connect (for the builder)
- Emby creates the plugin's root class and the start-up entry point (both in the root `TopPicksPlus` namespace), plus EmbyBridge's scheduled task, event listeners and API service.
- The entry point receives Emby's services, builds EmbyBridge's adapters with them, builds the **paths** record (programdata, Top Picks folder, plugin data folder) and the **log** (both plain types defined in Logic), then builds Store (and has it tidy leftover `*.tmp` files), Artwork and Run, handing each what it needs. It then fills EmbyBridge's static `Hooks` registry with Run's hook implementations (the full list is in the EmbyBridge README, including the missed-run hook) and a settings source: a small root class that reads and saves the Settings configuration class and turns it into Logic's settings record. Emby-created EmbyBridge classes reach Run and the settings only through that registry. Until it is filled, events are dropped (F6) and API calls answer "starting up" (after the administrator check, F8).
- Run uses Store, Artwork and EmbyBridge only through interfaces those parts define (`IStore`, `IArtwork`, the EmbyBridge adapter interfaces), so Run is tested with fakes.
- Run gets settings as a plain Logic record (through a hook argument or a settings-source interface defined in EmbyBridge) and never uses Settings; run state is in Store's state.json (D29).
- managed.json is only ever written by Run (the weekly steps and the order guard storing found IDs), through `IStore`, which holds one lock around each read-change-write of it. Store holds a lock around each read-change-write of plays.json and of state.json too.

## Before building (prerequisites, not open questions)
Read from the server before the chunk that needs it: the SkiaSharp version Emby loads (Artwork, D15), the .NET version Emby runs on (System.Text.Json, D30), and the exact names of the library-change and task events (EmbyBridge, F5). The first build chunk proves that a date added set by the plugin survives a full scan and a restart, and confirms which property is the Emby ID, how Latest orders series, that the row-check request doesn't leave out watched items, Emby's "played toggled" reason value, that Emby reports an item played at its "playback stopped" event (F6 "finished"), and that setting date added and the artwork refresh (local images only, nothing replaced from the internet, no metadata) leave the copy's .nfo, title and everyone's watched state unchanged (C34).

## Not included (on purpose)
- Different picks for different users. It's one shared row, like today.
- Trailers or "coming soon" items.
- A different number of picks.
- Hiding the copies from search.
- Changing anyone's watched state (D39).
- Taking over the old plugin's folders, or importing from Playback Reporting (D34).
