# Top Picks Plus – Stage 5 readiness review 2 (branch spec/readiness-fixes)

Reviewer: fresh agent, judged only from the files listed in the brief. No files changed.

## 1. Restatement (plain English)

Top Picks Plus replaces the old Top Picks plugin. Once a week (Sunday 05:00 UK time), or when you press "Run now", it picks 10 titles and puts them in the "Latest Top Picks" row on the Emby home screen, numbered 1 to 10 in the right order.

- **How it picks:** first any titles you have pinned (up to 10, movies or whole series, in your order). The rest are the titles most people watched in the last 7 full UK days. Each person who watched a title on a given day counts once ("viewer-days"), so one person binging a series doesn't beat several people watching a film. "Watched" means Emby marked it played, or they watched at least half of it (20 minutes if the length isn't known). Ties go to whatever got new content most recently. If not enough was watched, the newest additions fill the gaps.
- **What it does to your files:** for each pick it builds a "copy" in the top-picks folder: small .strm files that point at the real video, .nfo files with the title's details and age rating, the backdrop, logo, subtitles, and a numbered picture drawn to look like today's row. Your real films and series are never changed. Copies are built in a scratch folder first, then moved in. Titles that drop out have their folder deleted. Titles that stay are updated in place, so watched ticks are kept.
- **How the order is kept right:** after a rescan it sets each copy's "date added" directly in Emby (pick 1 newest, each next pick one hour older). It then checks the row the way a normal user sees it. Between runs, an "order guard" puts any dates back if a scan or restart changes them.
- **Plays and watched ticks:** it keeps its own 90-day log of who watched what, on the server only, visible only to admins. Watching a copy counts for the real title, and the watched tick or resume point is copied to the real title too.
- **What you see and control:** a settings page (admins only) for which libraries to choose from, pins, the user the row check looks through, and Run now. A report shows the last run: each pick and why it was picked, whether its copy and date were applied, the row check result, missing pins, failed artwork, and the last refused run.
- **Taking over from the old plugin:** the old plugin must be uninstalled first. While it is loaded, Top Picks Plus refuses to do anything (apart from logging plays in the first release). On its first real run it adopts the old plugin's folders (any folder holding a .strm and a .nfo). It deletes the ones that are no longer picks and replaces the ones that are with fresh copies. Anything else in the folder is never touched.
- **When things go wrong:** if Emby restarts mid-run, the run carries on with the same picks. An error is retried 5 minutes later, with at most 3 resumes in total. If the managed list is damaged, if the library is missing, or if the library has the wrong .nfo settings, the run refuses and deletes nothing. A damaged play log or run record is renamed and started fresh. If artwork drawing fails, the plain backdrop is used. If the row check fails twice, the run still counts and the report shows what Emby returned. If Emby was off on Sunday, a catch-up run starts 10 minutes after start-up (except right after first install).
- **Build order (D58):** (1) the play logger, released alone so data builds up while the old plugin still runs; (2) choosing; (3) copies, swap and takeover (the old plugin is uninstalled here); (4) order guard and resume; (5) watched sync; (6) settings page and report.

## 2. What I would have to guess

**Blockers**

1. **Plays on the old plugin's copies are lost during the data-gathering weeks.** Files: spec F6 ("looks the copy up in the managed list"), D28, D58, D59, D25. Under D58/D59, chunk 1 logs plays while the old plugin still runs the row. There is no managed list yet, so a play on an old-plugin copy (probably the most-watched route, since it is the home row) has no source to credit. plays.json says `sourceId` is "never the copy". The builder must choose between dropping these plays, logging them against the copy's ID (they would then never match a candidate), or resolving the source through the .strm target path. The same gap affects the Playback Reporting import (D25: "Movie → that movie"). Its history holds ItemIds of old Top Picks copies, which the old plugin deletes and recreates weekly, so those IDs may no longer exist. It also affects plays between installing chunk 3 and the first run (takeover only happens at the start of the first run, D38). Affects F6, F2, D25, D28, D58, D59, C10, C11, C27.
2. **The first-run import is a no-op under the build order.** Files: D46, D25, D58, F6, C27. D46 limits the Playback Reporting import (and the "last played" fallback) to plays from before `ListeningSinceUtc`, which is set when the plugin first starts (chunk 1). The import runs at the first run, which needs chunks 2–3 and comes at least a week later. By then the run's 7-day window is entirely after `ListeningSinceUtc`, so both paths import nothing. C27 ("the report says the first week came from Playback Reporting, and titles watched last week are in the list") then either can't fail or reports something misleading. Someone must decide whether to import at chunk-1 install, drop the import, or move `ListeningSinceUtc`. D58 also doesn't say which chunk is "the import chunk" that D25 asks to prove the SQLite read. Affects F6, D25, D46, D47, D58, C27, C58.

**Should fix**

3. **Who writes copy files: D30 vs D43.** D30 says "Logic builds the text … EmbyLink writes them". D43 (newer, the owner's) says Storage owns every file change. D30 is not marked as amended. Artwork/README.md line 6 still says EmbyLink saves files into copy folders. The EmbyLink README is half-updated. A builder following the READMEs would put file writes in EmbyLink, which D43 forbids. The boundary check can't catch this, because EmbyLink may use System.IO. Affects D30, D43, F3, F4.
4. **`<dateadded>` offset on clock-change Sundays.** Files: D50, Logic/README.md. D50 says Logic is given "the offset" (one value). UK clocks change at 01:00 UTC on a Sunday. On those Sundays the 05:00 run's picks 5–10 have rank dates before the change, so one offset gives wrong local times for half the row. In October the 01:00–02:00 local hour also happens twice. An offset per rank date is needed, and the ambiguous hour needs a rule. C62 tests one item on each side of a change, not one run that spans it. Affects D50, F3, F4, C62.
5. **Windows CI vs artwork tests.** D43 says the windows-latest job runs every test. D56 gives the test project only SkiaSharp.NativeAssets.Linux, so drawing tests (C43) will fail on Windows. Either add Win32 native assets (not decided) or skip artwork tests on Windows (not decided). Affects D43, D56, C43.
6. **SkiaSharp 2.88.3 vs the audit step.** D34/D56 pin 2.88.3 exactly. To my knowledge, NuGet's advisory database flags SkiaSharp below 2.88.6 (the libwebp CVE-2023-4863). The build.yml audit fails on any vulnerable package; its only exception is packages from the Emby SDK. D24 gives System.Text.Json a "newer patch if flagged" escape; D34/D56 have none. The first artwork chunk may be unable to pass CI without a new decision. Please verify. Affects D34, D56, D15, build.yml.
7. **Stryker scope and threshold contradict each other.** D57 says Logic **and Storage**, failing below 80%. Logic/README.md says "limited to this folder" with an unnamed threshold. CLAUDE.md says "added by the first Logic chunk". Storage's junction tests are skipped on Linux, where Stryker would run, so those mutants survive and drag the score down. Affects D18, D57.
8. **Old decisions not marked as replaced:**
   - D26 says "order guard paused while a run is `running`"; D44 says "only while the lock is held". This is the important one, and it is what C59 tests.
   - D34 Oswald vs D62 Anton. Artwork/README.md line 9 still says "Oswald Bold", and line 3 says "bold font".
   - D25 "played flag" vs D47.
   - D31's "fixed list" of refusals lacks `librarySetup` (D53).

   A builder reading top-down meets the old rule first. Affects D25, D26, D31, D34.
9. **"Up to 3 times in all" is ambiguous.** F1 could mean 3 attempts or 3 retries after the first. D39/D44 mean 3 resumes after the first attempt (4 tries). C59 says "at most 3 times". Affects F1, D39, D44, C59.
10. **The scheduled Sunday run while an earlier run is unfinished.** D44 covers Run now while a resume is waiting. Nothing covers the Sunday trigger, or the missed-run timer, firing while run.json says `running` with resumes left. Does it resume the old run (old picks) or start a new one (leftovers rule, D39)? Also unclear: whether a refusal condition found mid-run (library removed, managed.json unreadable) counts as an "error" to retry or as a refusal. Affects F1, D39, D44.
11. **D58 doesn't define chunks well enough to build or check.**
    - No chunk lists its checks.
    - The report and settings page (F8) come last, so C6–C10, C13, C23, C27 and C31 can't be seen by the owner until chunk 6.
    - Chunk 3 deletes real folders and uninstalls the old plugin before resume (chunk 4) exists, which contradicts D26's "a restart at any moment is safe".
    - Artwork, the "first .nfo chunk" (D50/C62), "the import chunk" (D25) and "the takeover chunk" (D59, C63) aren't mapped to D58's six steps.
    - D14's "first chunk loads in 4.10.2" has no C-ID.
    - Only chunk 1 is said to be released. It is unclear whether chunks 2–5 go to the server.

    Affects D14, D25, D50, D58, D59, every check.
12. **C64 has no test, and the scaffold may fail it.** BoundaryTests.cs uses NetArchTest `HaveDependencyOnAny` with prefixes such as "System.IO". As far as I know, 1.3.x matches by name prefix, so `System.IObservable<T>` would be reported. No decision says how to fix this, and tests/README.md says changing a boundary rule needs the owner. Affects C64 and the boundary check.
13. **Episode and season artwork are not specified.** F3 lists only series-level images. Without episode thumbs Emby may try to extract images through the .strm from N:\/K:\ (slow, and possibly failing), or show blanks. Nothing says whether source episode and season images are copied. Affects F3, D30, C16.
14. **No data-format version, and no rollback across chunks.** D17 rollback means "put the previous DLL back". An older DLL may meet a newer managed.json or run.json (new fields, states), and a rollback from chunk 3+ leaves no plugin filling the row. Nothing says whether files carry a version or what an older DLL does with an unknown shape (damaged → `dataDamaged` refusal?). Affects D17, D32, data.md.
15. **Which plays are logged.** F6 says "every item". Nothing says to ignore music, Live TV, trailers or home videos (D25 does say this for the import). It is also unclear which UK date a play that crosses midnight gets (start or stop). Affects F6, data.md plays.json, C10.
16. **D54 automatic checks only test the decision, not the wiring.** C26, C28, C29, C59 and C63 are EmbyLink behaviours (start-up timers, finding the library, the rescan wait, finding the old plugin). D54 tests only the Logic/Storage rule. The "owner's live check" for them is C20, which exercises none of these paths. This needs to be stated as an accepted gap, or these checks overclaim. Affects D54, C26, C28, C29, C63.

## 4. Confidence score: 71 / 100

The core design is strong and unusually well specified: the swap order, delete containment, takeover, resume, the counting rules and the artwork measurements all match the reference pictures. A builder could write Logic and Storage today with little guessing. The weak point is the chunk-1 data-gathering phase, which is the whole reason for D58's order. As written, plays on the old plugin's row aren't credited, and the Playback Reporting seed can never import anything. So the first weeks of data, the feature the owner chose to build first, may not do what the owner expects. Several newer decisions also contradict older ones that are still unmarked (D30/D43, D26/D44, D34/D62, the Stryker scope), and the READMEs a builder reads first still carry the old versions. CI decisions (Windows job + Linux-only Skia natives, the pinned SkiaSharp vs the audit) will probably break the first artwork or Storage chunk. The clock-change offset can put half the .nfo dates an hour out twice a year.

What would raise the score to 85+:
- An owner decision on items 1 and 2: how to credit plays on old copies during chunk 1, and when or whether to import.
- Marking D25, D26, D30, D31 and D34 as amended, and fixing the Artwork and EmbyLink READMEs.
- A per-chunk table in D58 that lists each chunk's checks and whether it is released, with resume shipped no later than the takeover chunk.
- A per-date offset rule in D50.
- Settling the Skia natives and audit for both CI jobs.
- Adding a test for C64.
- Turning C6–C8 and C13 into automatic Logic checks, and adding checks for the gaps listed in section 3.
