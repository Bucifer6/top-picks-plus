# Top Picks Plus – spec (v6, 2026-11-08)

**Purpose:** Every week, fill the "Latest Top Picks" row on the Emby home screen with the 10 titles people are watching most, numbered 1–10 in the right order every time, with no manual step. The owner can pin titles if they want to.

**Replaces:** the old third-party plugin Emby.TopPicks (file `Emby.TopPicks.dll`), abandoned and closed source. It orders the row by writing a "date added" into each title's .nfo file. Emby only reads that date the first time it sees a title, so when last week's folders are still there the order breaks (card 0001).

**Install (D34):** the owner uninstalls the old plugin, empties the top-picks folder by hand (its folders are only copies) and installs this plugin. Exact steps are in docs/releases.md. The plugin never adopts or imports anything from the old plugin: the first week's row is pins plus the newest titles, and real viewing takes over from the next week.

**Rigour level:** 1 – Personal: a home Emby server with a handful of users. No viewing history is kept: only how many people watched each title on each day, for 90 days (D21, D33).

## Words used here
- **Source title:** a real movie or series in the owner's normal libraries (for example N:\Movies, K:\Series). **Source item:** a source movie or source episode (the thing with a video file).
- **Emby ID:** an item's `Id` exactly as Emby's own API gives it, as text (on Emby 4.10 a number written as text). The first EmbyBridge build chunk confirms which Emby property this is (C34).
- **Movie or TV library:** an Emby library whose content type is "movies" or "tvshows". Mixed or other libraries are never used as sources.
- **Copy:** the Top Picks version of a source title: a folder of .strm, .nfo, subtitle and image files in the Top Picks folder. A .strm file is a one-line text file holding the full path of the real video file; Emby plays the real file through it. **Copy item:** the Emby item Emby makes for a copy (a copy movie, a copy series, or a copy episode).
- **Copy-looking folder:** a folder directly inside the Top Picks folder that holds a .strm file, in itself or one level down (a season folder). Used only by the missing-managed.json rule (F9).
- **Programdata:** Emby's data folder, given by Emby at start-up (here `C:\Users\Admin\AppData\Roaming\Emby-Server\programdata`).
- **Top Picks folder:** always `<programdata>\data\top-picks`. Fixed, not a setting (F9 "Finding the Top Picks library").
- **Top Picks library:** the existing Emby library whose only folder is the Top Picks folder. Its "Latest" home-screen row is the "Latest Top Picks" row. The plugin never creates or deletes libraries.
- **Plugin data folder:** `<programdata>\data\TopPicksPlus\` (D23). Holds managed.json, plays.json, run.json, run.previous.json, state.json, `staging\` and `backups\`. Never inside any library and never under `programdata\plugins`.
- **Date added:** Emby's own record of when an item was added (DateCreated). The Latest row shows the newest date added first.
- **Run start:** the moment Run creates this run's run.json (step 1, before anything else), in UTC. **Rank time** = run start rounded down to the whole minute. Both are stored in run.json and never change, even on resume. **Rank date** of pick N = rank time minus (N − 1) hours. **The run's UK day** = the UK day of the rank time.
- **UK day:** a calendar date in the Europe/London time zone (Windows: "GMT Standard Time"). EmbyBridge passes the zone and the current time into Run and Logic; Logic never reads the clock or the zone itself.
- **Managed list:** managed.json, the plugin's record of every copy it looks after (data.md). A folder is a **managed folder** only if it is on this list.
- **Candidate:** a title that may be picked (F2 step 5).
- **Viewer-day:** one user counted as watching one title on one UK day (F6).
- **Roll-up:** turning finished UK days' plays into daily counts, deleting their user IDs, and removing counts older than 90 days (F6, D33).
- **Can be reached** (a library folder): the folder exists and listing its top level succeeds within 30 seconds.
- **Run lock:** the one lock, held in memory inside the plugin (D32). A run holds it from its start to its end; the order guard holds it while it works (F5). It does not survive an Emby restart.
- **Waiting to resume (D36):** run.json exists, can be read, and its status is `running`, and no run holds the run lock. This only happens after Emby stopped during a run. Any other status (`finished`, `incomplete`, `failed`, `refused`) is never waiting, so a failed run can never block later runs.
- **Run statuses** (data.md run.json `status`):
  - `running`;
  - `finished`: every step done and nothing below made it `incomplete`;
  - `incomplete`: every step done, but at least one of: an operation was skipped with a note (F4 step 7); a pick got no copy (listed in `skipped` at step 5); a pick's copy hadn't appeared by the end of the step 8 wait. Episodes left out of a copy, drawing fallbacks, and a date or artwork refresh that didn't work are reported but don't make a run incomplete (the order guard puts dates right later);
  - `failed`: an error after step 1 (F4 "If something goes wrong"), a guard failing on resume at `swap` or later, or resume giving up (F5);
  - `refused`: a guard said no, or the backup failed, before anything in the Top Picks folder was changed (step 1, step 3, or a guard failing on resume at `guards` to `prepare`).
  A **successful run** is `finished` or `incomplete`.
- **Pending flags:** state.json's `historyLostPending` and `stateResetPending` (data.md). At step 1 and again at step 12, each one that is true is set true in run.json (`historyLost`, `stateReset`; never set back to false), run.json is written, and only then is the flag cleared in state.json. Repeating this is harmless, so a stop between the two writes loses nothing.
- **Text comparisons** for ordering and ties are ordinal (character by character, not by language rules); "ignoring case" means ordinal ignoring case. Paths are compared as full resolved paths, ignoring case.

## F1 – When it runs
- Emby scheduled task **"Refresh Top Picks"**, default trigger every **Sunday at 05:00 on the server's clock**. The server is set to UK time; if the server's time zone isn't Europe/London, the run still happens and the report warns about it.
- **Run now (D35):** the settings page's Run now button asks Run directly (through EmbyBridge's API and the start-run hook). Run takes the run lock in that same call, so a second press is turned down at once. The run then carries on in the background, and the settings page shows "run in progress" until it ends. It does not show in Scheduled Tasks. The task's own Run button in Scheduled Tasks starts the task as usual.
- **One run at a time (D32, D36).** Every way of starting a run (the task, Run now, resume, the missed-run rule) goes through one Run entry, which takes the run lock. Run now, the task and the missed-run rule are turned down if a run holds the lock or a run is waiting to resume: the settings page says "a run is already in progress", and a task start returns at once with that message in the report log. If only the order guard holds the lock, the start waits for it to finish (at most 2 minutes; after that it is turned down the same way). Only resume may take the lock while a run is waiting to resume. Emby's own task queue is not relied on; if Emby queues a second task start, it runs later as an ordinary run, which is safe (C3).
- run.json records what started each run (`trigger`: `task`, `run now`, `missed run`). Emby doesn't tell the task whether its Sunday trigger or its Run button started it, so both are `task`. A resumed run keeps its trigger and sets `resumed`.
- **Start-up order** (timers owned by EmbyBridge, each calling a Run hook). Before any timer starts, the root entry point has Store tidy its folder (leftover `*.tmp` files, F9).
  1. +1 minute: roll-up (F6).
  2. +2 minutes: order guard (F5), unless a run holds the lock or a run is waiting to resume.
  3. +3 minutes: resume, if a run is waiting to resume (F5).
  4. +10 minutes: **missed-run rule**: if no run holds the lock, no run is waiting to resume, and state.json's last successful run is more than 7 days ago, or there has never been one (first install), start a run (`missed run`).
- Also every day at 00:05 UK time: roll-up (D33).
- `failed` and `refused` runs don't count as successful, so the missed-run rule tries again at the next start-up.

## F2 – Choosing the 10 (fully automatic)
No manual step is ever needed. Pins are optional. All of this is Logic, tested without Emby.
1. **Pins (optional) first**, in the owner's order. A pin can be any movie or series in any movie or TV library except the Top Picks library. A pin is **missing** if its source title is gone, is no longer a movie or series in a movie or TV library, or a movie's video file can't be found, or a series has no episode whose file can be found ("can be found" = EmbyBridge's source-files adapter says the file exists, D28). Missing pins are skipped and the rest move up; each is listed in the run report (with its last-known title from state.json) and marked "missing" on the settings page. Duplicates are removed when settings are saved (F8); if the settings file holds duplicates or more than 20 pins anyway (edited by hand or restored), Run keeps the first of each and the first 20. Only the first 10 usable pins are used.
2. **The remaining places go to the most watched candidates**, by **viewer-days in the 7 UK days before the run's UK day** (for a Sunday run, the previous Sunday to Saturday). Plays on the run's own day count next week. Episodes count towards their series. A pinned title isn't picked again.
3. **Order, first to last** (for watched titles; filler uses b–e):
   a. more viewer-days first;
   b. newest content first: a movie's date added; a series' newest available episode's date added;
   c. newer premiere date first; no premiere date goes after one that has it;
   d. title, A to Z, ignoring case;
   e. source Emby ID, ordinal, lowest first (so the order is always the same).
4. **Filler:** if fewer than 10 places are filled, the rest go to candidates nobody watched, ordered by 3b–3e. On the first run after install (no plays yet) every unpinned place is filler.
5. **Candidates:** movies and series in the chosen libraries (default: every movie and TV library apart from the Top Picks library). At step 1 the chosen library IDs are checked again: one that no longer exists or is no longer a movie or TV library is ignored and the report says so; if libraries were chosen and none of them is still usable, the run is refused. Logic itself drops anything in the Top Picks library or with a file under the Top Picks folder, whatever the settings say. A title appears once per Emby ID (the same film in two libraries is two titles). A movie is left out if its video file can't be found. A series is left out only if none of its episode files can be found; missing episodes are left out of its copy.
6. With fewer than 10 candidates the row is shorter. The run doesn't fail.
7. **Always 10.** The number of picks is fixed (D11).
8. **Offline drives (D25):** at F4 step 1, every folder of every chosen library, and of every pinned title's library, must be reachable (EmbyBridge's source-files adapter, D28). If any can't, the run is **refused** and the report names the folder.

## F3 – What each copy contains
**One naming rule for every folder and file the plugin makes** (Logic, `SafeName`):
- Remove `< > : " / \ | ? *` and control characters, turn runs of spaces into one space, then trim leading spaces and trailing dots and spaces.
- If the result is empty, or a name Windows reserves (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, any case, with or without an extension), use the fallback given (always the item's Emby ID).
- Shorten to the length limit at a whole character, then trim again.
- **Lengths:** copy folder name at most 60 characters; episode file name (before the extension and language parts) at most 80. Every full path, including the 8-character temporary suffix `.tpp-tmp` (F4 step 7), must be at most 240 characters both in the Top Picks folder and in `staging\` (Logic checks the longer of the two). If a path is too long, the episode title part is shortened; if it still can't fit, that episode is left out and the report says so.
- Names are compared ignoring case when checking for clashes, as Windows does.

**Names:**
- **Copy folder:** `Title (Year)`, or `Title` with no year; fallback the source ID. If two picks get the same name, or the name is already used (ignoring case) by any folder in the Top Picks folder (managed or not, including a managed folder being deleted this run), the name is cut to 55 characters and ` - 2`, ` - 3` … added until free. The plugin never writes into a folder that isn't managed.
- **A title that stays keeps its folder name** for as long as it stays, even if its title or year changes, so Emby keeps the same item. A new name is only used when a title comes back after dropping out.
- **Movie files:** `<folder>.strm` and `<folder>.nfo`. The .strm points to the movie's main video file (for a movie with several versions, the one Emby plays by default).
- **Series:** `tvshow.nfo` in the copy folder, then one folder per season: `Season 1`, `Season 2` … (`Specials` for season 0). Episode files are `<Series> - S01E02 - <Episode title>` (`.strm` and `.nfo`), where `<Series>` is SafeName of the source series' name cut to 40 characters, and numbers are padded to at least 2 digits. With no episode title: `<Series> - S01E02`. A video file holding several episodes gets one .strm named with its first and last, `S01E01-E02`, and its managed entry lists every episode it holds. An episode with no season or episode number goes in `Specials` as `<Series> - S00E<Emby ID>`.
- **Subtitles:** for movies and episodes, external subtitle files (.srt, .ass, .ssa, .vtt, .sub) next to the source video are copied (read through the source-files adapter, D28), keeping the source's language and forced/default parts: `<copy file name>.en.forced.srt`.
- **The .strm content** is exactly the source file's full path and nothing else. If the path contains a line break (CR or LF), that item is left out and reported.

**.nfo files** are written with an XML writer (any text from Emby is escaped, never pasted in raw; characters XML doesn't allow at all are removed first), UTF-8:
- Movie: `title`, `originaltitle`, `year`, `premiered` (yyyy-MM-dd), `plot`, `mpaa` (age rating), `genre` (one per genre), `runtime` (minutes), `uniqueid` (each provider ID, e.g. imdb, tmdb), `dateadded`.
- Series (`tvshow.nfo`): `title`, `originaltitle`, `year`, `premiered`, `plot`, `mpaa`, `genre`, `uniqueid`, `dateadded`.
- Episode: `title`, `showtitle`, `season`, `episode`, `aired`, `plot`, `runtime`, `mpaa`, `uniqueid` (each provider ID the source episode has; for a multi-episode file, those of its first episode), `dateadded`.
- The `uniqueid` lines are what make Emby share watched state between a copy and its real title (D39, F7). They are always written when the source has them.
- `dateadded` is the rank date in **UTC**, `yyyy-MM-dd HH:mm:ss`, so the autumn clock change can't make two ranks share a time. Every episode of a series gets the series' rank date. The plugin also sets the date itself at F4 step 9; if Emby ever re-reads the .nfo as local time, every copy moves by the same amount, so the order still holds, and the order guard puts the exact values back.

**Artwork** (images come from EmbyBridge as bytes; Artwork never touches files):
- `fanart.jpg`, or `fanart.png` if the source backdrop is a PNG: the source's first backdrop, as-is.
- `logo.png`: the source logo, if there is one.
- `backdrops\theme.mp4`: the source theme video, if there is one, copied (opened through the source-files adapter) only when a copy is first created. An update keeps it as it is.
- `folder.png` and `thumb.png` (the same picture), drawn at **1000×562** (D6) with the embedded font **Montserrat ExtraBold** (SIL OFL, D15):
  - Background: the backdrop scaled to cover the whole picture, centred. No backdrop: the poster, scaled to the full height and centred on dark grey `#111111`. Neither: plain `#111111`.
  - A dark fade over the left 45%: 70% black at the left edge to clear at 45%.
  - The rank number in white. The font size is chosen so the digit "0" is 390 px tall (measured from the drawn glyph), the number starts 40 px from the left edge and is centred top to bottom. If the number is wider than 360 px ("10"), it is scaled down to 360 px wide, so it never reaches the logo box.
  - The logo fitted inside the box x 420–960, y 60–300, keeping its shape, centred in the box. No logo: the title in white in the same box, at most 2 lines, as large as fits between 72 px and 36 px, then cut with "…".
  - **If drawing fails** (an image that can't be read, or SkiaSharp can't load; Artwork catches any `Exception` around its drawing calls): the copy's `folder` and `thumb` pictures are the source backdrop (or, with no backdrop, the poster) saved as-is with their own extension (`folder.jpg` / `thumb.jpg` for a JPEG). With neither image, there is no folder picture. The report says drawing failed for that title.
  - Whatever is written, the copy ends up with only one `folder.*` and one `thumb.*`: an old one with another extension is removed (F4 step 7 "update").

## F4 – Each week's update, in order
Run carries out these steps. run.json's `step` names the step in progress (the value is given in brackets after each step's name), so a restart can carry on (F5). A run that refuses changes nothing in the Top Picks folder.
1. **Create the run and refuse or go** (`guards`): Store copies the previous run.json to run.previous.json **only if that run was successful** (so run.previous.json always holds the last successful run before this one, and failed or refused runs never hide it). Then it writes the new run.json: new `runId`, `startedUtc` (run start), `rankTimeUtc`, `trigger`, `resumed` false, `resumeCount` 0, `step` `guards`, status `running`, every list empty, every true/false false, `rowCheck.result` `not run`. Then the pending flags are carried over (see "Pending flags"). Then the guards, in order: old-plugin guard, finding the Top Picks library (F9), damaged or missing managed.json (F9), chosen libraries still usable (F2 step 5), offline-drive check (F2 step 8). If any fails, status `refused`, the report says why, and nothing else is changed. (A resumed run does not create run.json again: F5.)
2. **Roll-up** (`rollup`) the play log (F6). Safe to repeat.
3. **Back up** (`backup`, F9) into `backups\YYYY-MM-DD-HHMMZ\` (the run start, UTC). If the backup fails, the run is refused (nothing has been changed yet).
4. **Choose** (`choose`) the 10 (F2).
5. **Plan** (`plan`): first tidy leftovers in managed.json: an `incoming` entry whose folder is in the Top Picks folder becomes `active`; an `incoming` or `active` entry whose folder isn't there is removed (if that title is picked again, it is planned as an add with a fresh folder). Then compare the 10 with the managed list and write, in one write of run.json, `picks`, `missingPins`, `ignoredLibraries`, `skipped` and every operation, before anything is changed: `delete` a drop-out, `update` a stayer, `add` a new title. Each `update` and `add` holds the **full planned managed entry** (folder, source, kind, rank, rank date and the file list with each .strm's source items), so the swap and a resumed swap never need to work it out again. A pick whose copy can't be planned at all (for example its every episode was left out) gets no operation and is listed in `skipped`.
6. **Prepare** (`prepare`): Store empties `staging\`. Run writes every new title's whole copy, and every stayer's whole new set of files (everything except `backdrops\theme.mp4`), into `staging\<copy folder name>\` with the same layout it will have in the Top Picks folder. Emby never sees `staging\`.
7. **Swap** (`swap`), one operation at a time, in the order **deletes, then updates, then adds**, each marked done in run.json when it finishes:
   - **delete:** if its folder is still there, delete it through the delete guard (F9); then remove its entry.
   - **update:** the same folder is kept. Each file from staging is written into the folder under a temporary name (`<name>.tpp-tmp`) and then renamed over the old file. Then every file in the folder that is not in the new set is deleted through the delete guard, except `backdrops\theme.mp4`; so the folder ends up exactly matching the new copy (an episode that has gone, an old `folder.jpg` next to a new `folder.png`, and any leftover `.tpp-tmp` file are all removed). Then the entry is replaced by the operation's planned entry, keeping the copy item IDs already found (the copy's `itemId`, and each file's `itemId` where its path is unchanged); `state` stays `active`.
   - **add:** write the operation's planned entry to managed.json as `incoming` (if it isn't there already), move its folder from `staging\` into the Top Picks folder (a move within the same drive, since both are under programdata; a folder move is a single rename), then mark the entry `active`. So a folder in the Top Picks folder is never unknown to the managed list. If the folder is already in the Top Picks folder and gone from staging (a resumed run), it was already moved: just mark the entry `active`.
   - Any operation that can't be completed (a guard check fails, the target of an add already exists while its staging folder is still there, a file can't be written) is skipped with a `note` in run.json, and the run will end `incomplete`.
8. **Rescan** (`rescan`) only the Top Picks library, and wait until every copy is in the library: for a movie, its copy item; for a series, the copy series and a copy episode for every .strm in its managed entry. Up to 15 minutes, or 30 minutes if any series' managed entry lists more than 200 .strm files. Each copy item's Emby ID is stored in managed.json as it is found.
9. **Set the order** (`dates`): for every copy item that has appeared, set its date added to its rank date (for a series, the series and every episode; if the first build chunk shows Emby orders series in Latest by "date last media added", that is set too, C34). The same date is already in the .nfo (card 0001). Before any change, EmbyBridge checks that the item's path is inside the Top Picks folder (Logic's path check), and refuses the change if not (F9). **The plugin never changes anyone's watched state or resume point** (D39, F7).
10. **Refresh artwork** (`artwork`) for each copy that has appeared, so the number on the picture matches. Then read each date added back and set it again if the refresh changed it.
11. **Check the row** (`check`, D22): ask Emby for the Latest Top Picks row as the apps do (the "latest items" request for the Top Picks library, 10 items, grouped by series), as the **check user**: the first user, by user ID (ordinal), who isn't an administrator, isn't disabled and can see the Top Picks library; if there is none, the first administrator the same way, and the report says so. The request does not leave out items the check user has watched, so a pick they have watched still counts (the first EmbyBridge chunk confirms the request; C34).
    - **Expected** = the picks whose copy is `active` and appeared at step 8, that the check user is allowed to see, in rank order. Every pick not expected is listed in `leftOut` with why: `no copy` (skipped), `not appeared`, or `parental controls` (the check user isn't allowed to see it).
    - Each returned item is matched by its Emby ID to the managed list. An episode (Emby sometimes returns one instead of its series) counts as its series. An item that matches no managed copy is reported by name and makes the check fail.
    - **passed** = the returned titles, in order, are exactly the expected picks, and every pick left out was left out only for `parental controls`. **partial** = the returned titles, in order, are exactly the expected picks, and at least one pick was left out for `no copy` or `not appeared`. **failed** = the returned titles are not exactly the expected picks in order (something missing, extra, unmatched or out of order). **not run** = the run stopped before this step.
12. **Record** (`done`): first state.json's `lastSuccessfulRunUtc` (and each pin's last-known title), then run.json: status `finished` (or `incomplete`, as defined in "Words used here"), `finishedUtc`, `step` = `done`, with the pending flags carried over again (so damage found during this run shows in this run's report). Release the lock. Run the order guard once. (If Emby stops between the writes, resume repeats from step 8, which is harmless.)

**If the step 8 wait runs out:** steps 9–11 run for every copy that has appeared, the status is `incomplete`, and the order guard (F5) sets the dates of the rest when they appear. Copies that appear late already carry the right number on their folder.png.

**If something goes wrong** (an error, not a restart) at any step after step 1: the run stops, the status is `failed`, `step` = `done`, and the report says which step and what failed in plain words; before step 7 it adds "nothing in the Top Picks folder was changed". No operation is undone. The lock is released. The order guard keeps the row ordered for the copies in place. The next run starts fresh (step 5 tidies leftovers).

**Errors never reach Emby:** every hook, timer, event handler and API action catches every error. In a run, an error makes the run `failed` as above; anywhere else it is logged and that one action is dropped. **What an error log line holds:** where it happened (hook, step) and the error's type name only, never its message or stack, wherever the action concerns a user (plays, the start list, user data); elsewhere the message may be logged at Debug, and never a user ID or user name (F6).

## F5 – Order guard and resume
- **Order guard:** 2 minutes after Emby starts, once after every run (successful or not), and 2 minutes after the last Emby library change to a Top Picks item (item added or updated in the Top Picks library: EmbyBridge waits for 2 quiet minutes, so a full scan triggers it once at the end). It takes the run lock only if it is free; if a run holds it, or a run is waiting to resume, or managed.json is damaged or missing, it does nothing. While it holds the lock, a run start waits for it (F1). For each `active` entry in managed.json it compares the copy item's date added (the series and each episode, and the series' "date last media added" if C34 showed Latest uses it) with its rank date and sets any that differ by more than 1 second. It finds copy items by the IDs in managed.json; an ID that is null or no longer exists is looked up by path (folder or .strm path) and stored; if nothing is found, that copy is skipped until next time. It only sets dates: it never refreshes artwork, changes files or touches watched state. It releases the lock when it ends, however it ends. The exact Emby events are confirmed in the first EmbyBridge build chunk (C4, C32).
- **Resume (D36):** at +3 minutes after start-up, if a run is waiting to resume, Run takes the run lock (the one start allowed while a run is waiting), sets run.json `resumed` true and adds 1 to `resumeCount`. If `resumeCount` is now above 3 (Emby stopped during the same run three times), the run is not tried again: status `failed`, `step` `done`, message "gave up after 3 restarts", lock released. Otherwise, by run.json `step`:
  - `guards` to `plan`: carry on from step 1's guards **without creating run.json again**: every field already in run.json is kept (`runId`, run start, rank time, `trigger`, `resumeCount`, `historyLost`, `stateReset`), run.previous.json is not touched, and the pending flags are carried over again (harmless, they only add). Steps 2–5 then run as normal; step 5 replaces `picks`, `missingPins`, `ignoredLibraries`, `skipped` and `operations` in one write. Each of these steps is safe to repeat: guards only read; roll-up repeats harmlessly; the backup is skipped if this run's backup folder is complete. If a guard now refuses, the status is `refused`.
  - `prepare`: run the guards again (a guard that fails makes the status `refused`, since nothing in the Top Picks folder has been changed), then Store empties staging and step 6 starts again.
  - `swap`: run the guards again, then carry on from the first operation not marked done, using the planned entries in run.json and the files already in staging. Repeating is safe: a delete whose folder has gone just removes its entry; an update's files are written again; an add follows the add rules in F4 step 7. If an operation can't be finished (its staging folder is missing and the target isn't there), it is skipped with a note, and the run ends `incomplete`.
  - `rescan`, `dates`, `artwork`, `check`: run the guards again, then start again from step 8 (each is safe to repeat).
  - A guard that fails on resume at `swap` or later makes the status `failed` with the guard's message.
  - Any error during resume is handled as any other run error (F4): status `failed`, lock released. So a run can never stay waiting to resume after its resume has been tried.
- What the row may show while a run is in progress: for a few minutes, a mix of last week's and this week's titles. When the run finishes, the row is complete and in order.

## F6 – Counting plays
- EmbyBridge listens for Emby's "playback started", "playback stopped" and "user data changed" events and passes them to Run's record-play hook. It ignores trailers, extras and anything that isn't a movie or an episode.
- **Which title it counts for:** a play on a copy item counts for the source title. The copy is found in the managed list by its path (each managed .strm lists the source items it holds, data.md). If managed.json is damaged or missing, a play on a copy can't be matched and is dropped (logged at Debug without user). A play on a source item counts for its movie or series, wherever it was started.
- **Runtime** of what was watched is always the **source** item's runtime (for a copy, the first source item its .strm holds), never the copy's.
- **Minutes watched in a sitting** = the stop position minus the start position (from the matching "playback started", held in memory only, by Run), in whole minutes rounded down, never below 0 or above the runtime. If the start wasn't seen (for example Emby restarted), the stop position is used. The in-memory start list holds at most 1,000 entries; entries older than 24 hours, and the oldest when it is full, are dropped.
- **Finished** = at "playback stopped", Emby reports the item as played for that user (Emby does this itself when playback passes its own "played" point).
- **Marked by hand** = a "user data changed" event that sets a movie or episode (source or copy) to played while that user has no playback of it in progress. It adds a sitting with 0 minutes and `markedPlayed` true, on the UK day it happened. Clearing played state adds nothing and removes nothing already recorded. Because a copy and its real title share watched state (D39), Emby may report one mark on both; both count for the same title and day, so that user still counts once.
- **Which users count:** every Emby user, administrators included.
- **What counts as watched:** a user counts for a title on a UK day if, that day, they finished an item in it or marked one played by hand, or their minutes on the title that day add up to at least 50% of the runtime, or 20 minutes when the runtime isn't known. For a series, the runtime is that of the episode watched, and each episode is judged on its own: one qualifying episode is enough. Two sittings of the same film at 30% each count. A sitting belongs to the UK day on which it stopped.
- **No viewing history (D21, D33):** who watched what is held only in plays.json's `today` section, so each person is counted once a day. **Roll-up** happens 1 minute after start-up, at 00:05 UK time every day, and at F4 step 2: every `today` entry from a UK day before the current one is turned into "title, day, number of viewers", and those entries (with their user IDs) are deleted, in one atomic write. A day is rolled up once: its entries are deleted in the same write that adds its counts. Daily counts more than 90 days before the current UK day are removed at every roll-up. Store keeps one lock around every change to plays.json, so the listener and a run never overwrite each other.
- Plays seen before start-up has finished wiring the plugin are dropped (logged at Debug without user).
- **Logging:** plays are never logged at Info level. The plugin never puts a user ID or user name into any log line or error message; Debug lines may name a title. Errors on these paths log only where and the error type (F4).

## F7 – Watched status (D39)
- **A copy and its real title share watched state.** Each copy's .nfo files carry the source's provider IDs (`uniqueid`, F3), and Emby itself shares watched ticks and resume points between items with the same provider IDs, as it does with the old plugin today (owner's proof test, D39). So finishing a film from the row marks the real film watched, and a half-watched film can be resumed from the row or from the real title.
- **The plugin never changes anyone's watched state or resume point**, on a copy or on a real title. No part has a way to do it (F9).
- **Known limitations, accepted by the owner:** a user who has "hide watched from Latest" turned on may see fewer than 10 titles in the row once they have watched some picks (D39). Copies appear in search next to the real titles, as they do today.
- Episodes carry their own provider IDs too (F3); C14 shows whether Emby shares their state the same way.

## F8 – Settings page and run report (Dashboard → Plugins → Top Picks Plus)
- **Administrators only.** Every action of the plugin's API (save settings, pin search, check pins, Run now, run status, read the report) first takes the signed-in user from Emby's own authorisation of the request, never from a user ID in the request, and refuses anyone who isn't an Emby administrator with "Administrators only" and no data. This check comes before anything else, even before "starting up" (Logic's admin rule, C70). Hiding the page is not relied on.
- **Libraries** to choose from (movie and TV libraries only). The Top Picks library is never offered.
- **Pins:** search for a movie or series, add it, drag to reorder, remove. When the page opens it asks the API's **check pins** action which pins are missing now (the F2 step 1 rule, live), and marks them "missing"; the report shows which were missing at the last run.
- **Saving checks every value** (EmbyBridge's API, on the server, using Logic's save rules with the facts EmbyBridge looked up): library and pin IDs must be Emby IDs that exist and are a movie or TV library, or a movie or series in one; the Top Picks library and its items are refused; duplicate pins are removed; at most 20 pins. A bad value is refused with a plain message and nothing is saved. Good values are saved through Emby's plugin configuration (the Settings part's configuration class). A settings file changed outside the page is checked again by Run (F2 steps 1 and 5).
- **Run now** button (F1, D35), plus a status line read from the run-status API: "run in progress", "waiting to resume after a restart", or the last run's status.
- **Last run report:** plugin version and Emby version; what started it and whether it was resumed; when it ran; status (finished / incomplete / failed / refused) and a plain-words message; each pick with rank, title, why it was picked (pinned / N viewer-days / filler) and whether its copy, date, artwork drawing and artwork refresh worked; skipped items and why; missing pins; ignored libraries; the row check result (passed / partial / failed / not run, which kind of user was used, what was left out of the expected list and why, and exactly what Emby returned if it didn't pass); total viewer-days in the 7-day window; whether popularity history was lost (damaged plays.json) or run state was reset (damaged state.json); a time-zone warning if needed. If the last run was `refused` or `failed`, the page also shows the last successful run (run.previous.json). No user names or IDs appear anywhere.
- **Text from Emby** (titles, names, messages) is put on the page as plain text only, never as HTML.

## F9 – Safety
- **Finding the Top Picks library:** the Top Picks folder is `<programdata>\data\top-picks`. The run is refused if no library has it as a folder, if more than one does, if the library holding it has any other folder, if the Top Picks folder or the plugin data folder is itself a junction or symbolic link, or if the Top Picks folder is inside, or contains, any other library's folder, the plugin data folder or programdata itself (other than being under it). All of these comparisons use full resolved paths, ignoring case. **Who does what:** EmbyBridge gives the libraries and their folders, and its source-files adapter gives each other library folder's resolved path (read-only); Run resolves the Top Picks folder and checks it isn't a link; Store resolves the plugin data folder and checks it isn't a link (through `IStore`); Logic makes every comparison.
- **Before every write, move, delete or replace** in the Top Picks folder or `staging\`, Run checks (and skips and reports the item if any check fails):
  1. the target folder is on the managed list (for a file: it is inside a managed folder), or is inside `staging\`;
  2. a copy folder's name is a single name (no `\`, `/`, `..` or drive letter), and each part of a file's path inside the folder is a single name;
  3. its real location, with every shortcut resolved, is directly inside the Top Picks folder (for files: inside the managed folder), or inside `staging\`;
  4. neither it nor any folder on the way to it is a junction or symbolic link, and deleting never follows one: a link found inside a managed folder is removed as a link, never entered.
  **In practice:** the plugin deletes only folders on the managed list and the files inside them. If someone puts their own file inside a managed folder, it goes when that folder is deleted or updated. Unmanaged folders and loose files in the Top Picks folder are never touched. `staging\` can never be on the managed list (managed names are folders directly in the Top Picks folder).
- **Emby items the plugin changes:** only date added (and "date last media added" if C34 needs it) and artwork refresh, and only on items whose path is inside the Top Picks folder. EmbyBridge checks each item with Logic's path rule before every change and refuses if not. EmbyBridge has no action that changes played state or resume points on any item (D39).
- **Store's own deletes** (emptying `staging\`, pruning `backups\`, removing old damaged run.json and state.json files, deleting a damaged plays.json, removing leftover `*.tmp` files at start-up) are only ever inside the plugin data folder, with the same real-location and no-link checks, and backups are only pruned by their own name pattern (`YYYY-MM-DD-HHMMZ`).
- **Old-plugin guard:** if Emby has loaded a plugin whose assembly is `Emby.TopPicks`, every run is refused and the report says to uninstall it first. Nothing else is matched by name.
- **Damaged files (D37).** A file is **damaged** if its contents can't be read as JSON, it has a `schemaVersion` the plugin doesn't know, or any field breaks data.md's rules (wrong type, value out of range, missing required field, a folder name that isn't a single name, a path that leaves its folder). A file that can't be **opened or read at all** (locked by another program such as antivirus, a disk error) is **not** damaged: it is left alone, and the action that needed it fails as an error (a run ends `failed`; a play or roll-up is dropped and logged, and the roll-up tries again next time). A missing file is not damaged either (data.md says what each missing file means).
  - **managed.json** damaged: left exactly where it is and every run is refused until it is fixed. A **missing** managed.json while the Top Picks folder holds a copy-looking folder is treated the same way (Store reports the file missing; Run looks for copy-looking folders, since only Run reads the Top Picks folder). The report gives the fix, which is the same as installing: stop Emby, empty the top-picks folder (keeping any folder you made yourself), delete managed.json, start Emby, Run now. The order guard and play matching on copies do nothing while it is damaged or missing (F5, F6).
  - **state.json** damaged: renamed to `state.json.damaged-YYYYMMDD-HHMMZ` and replaced by an empty one with `stateResetPending` true; the run carries on and the report says run state was reset (the missed-run rule may start an extra run, and missing pins show no title until the next run). The newest 3 such files are kept. It holds no user IDs.
  - **run.json** damaged: renamed to `run.json.damaged-YYYYMMDD-HHMMZ`; there is nothing to resume, and a fresh run can start. The newest 3 such files are kept. It holds no user IDs. (run.previous.json damaged: it is ignored and overwritten at the next successful run's step 1.)
  - **plays.json** damaged: **deleted at once**, because it may hold user IDs and can't be read to roll them up; counting starts again from empty, `historyLostPending` is set, and the report (of this run if a run is in progress, otherwise the next) says the popularity history was lost. The daily counts can be put back by hand from the newest backup (stop Emby, copy its plays.json over, start Emby); backups never hold user IDs and load as a normal plays.json (C63).
  - Damage is noticed whenever Store reads the file (a run, a roll-up, a play, the order guard), and handled the same way each time.
- **Backups:** at F4 step 3, plays.json **with its `today` section emptied** (`"today": []`, so no user IDs and still a valid plays.json) and `TopPicksPlus.xml` (copied as a file, never read) are copied into `backups\YYYY-MM-DD-HHMMZ\`, then an empty `complete` file is written last; a folder without `complete` is unfinished and is not counted. Files that don't exist yet are skipped. The 8 newest complete folders are kept. To restore popularity counts or settings: stop Emby, copy the file back over the live one, start Emby. managed.json and state.json are not backed up: neither can be usefully restored (D37).
- **Personal data:** none is kept (D21, D33). Today's not-yet-counted plays hold user IDs until the next roll-up after their day ends. Nothing is sent anywhere; the plugin makes no network calls (no part may use `System.Net`).
- **Age ratings:** each copy's .nfo carries the source title's age rating, so Emby's parental controls apply to copies as to the originals.

## F10 – Staying working through Emby updates
- The build targets a fixed Emby plugin SDK version (D14).
- After every Emby server upgrade, the owner runs check C20. The plugin writes its version and the Emby version at the top of each run report.

## How the parts connect (for the builder)
- Emby creates the plugin's root class and the start-up entry point (both in the root `TopPicksPlus` namespace), plus EmbyBridge's scheduled task, event listeners and API service.
- The entry point receives Emby's services, builds EmbyBridge's adapters with them, builds the **paths** record (programdata, Top Picks folder, plugin data folder) and the **log** (both plain types defined in Logic), then builds Store (and has it tidy leftover `*.tmp` files), Artwork and Run, handing each what it needs. It then fills EmbyBridge's static `Hooks` registry with Run's hook implementations (the full list is in the EmbyBridge README) and a settings source (reading and saving the plugin's configuration). Emby-created EmbyBridge classes reach Run and the settings only through that registry. Until it is filled, events are dropped (F6) and API calls answer "starting up" (after the administrator check, F8).
- Run uses Store, Artwork and EmbyBridge only through interfaces those parts define (`IStore`, `IArtwork`, the EmbyBridge adapter interfaces), so Run is tested with fakes.
- Run gets settings as a plain Logic record (through a hook argument or a settings-source interface defined in EmbyBridge) and never uses Settings; run state is in Store's state.json (D29).
- managed.json is only ever written by Run (the weekly steps and the order guard storing found IDs), through `IStore`, which holds one lock around each read-change-write of it.

## Before building (prerequisites, not open questions)
Read from the server before the chunk that needs it: the SkiaSharp version Emby loads (Artwork, D15), the .NET version Emby runs on (System.Text.Json, D30), and the exact names of the library-change and task events (EmbyBridge, F5). The first build chunk proves that a date added set by the plugin survives a full scan and a restart, and confirms which property is the Emby ID, how Latest orders series, and that the row-check request doesn't leave out watched items (C34).

## Not included (on purpose)
- Different picks for different users. It's one shared row, like today.
- Trailers or "coming soon" items.
- A different number of picks.
- Hiding the copies from search.
- Changing anyone's watched state (D39).
- Taking over the old plugin's folders, or importing from Playback Reporting (D34).
