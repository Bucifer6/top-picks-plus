Spec v3 answered every v2 finding, but backups, resume, damaged files and takeover each added a rule that clashed with something else: the F4 step order, a run.json field, a part's "must not use", or D21.
Do instead: after writing a new rule, check it against (1) the F4 step list and run.json `step`, (2) every data.md field it reads or writes, (3) the README walls of the part that does it, (4) the decisions. Fix the clash in the same edit. When a feature is removed, also re-read every rule that mentions what it touched (here: played state) and ask whether its meaning changed. When a new rule runs before or around older ones (a pre-check, a lock, a wait), walk one concrete case **of every operation kind** (delete, update, add, and each resume point) through every older rule it now touches; one example is not enough (v8 missed the update). Also walk with **something the plugin didn't make** (a file with an odd name, a link) inside each folder, and with **several starts at once where the first run ends quickly**. When a rule changes **how** something is reached (a path form, a lock holder), walk **every action** on that thing (list, read attributes, test for a link, write, delete), and try a wrong-kind or read-only one too. Before adopting any API or library a reviewer suggests, check it exists on the decided target (D14: netstandard2.0).
