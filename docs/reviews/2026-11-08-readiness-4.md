## 1. Restatement (plain English)

**What it is.** Top Picks Plus is an add-on ("plugin") for the owner's Emby media server. It replaces an old, abandoned add-on (Emby.TopPicks). Every week it fills the home-screen row called "Latest Top Picks" with 10 films or series. Each one has a big number 1–10 on its picture, and the row always shows them in order 1 to 10, left to right. The owner never has to do anything by hand. If they want to, they can "pin" titles to force them into the top places.

**How the row works.** The row is Emby's normal "Latest" row for one special library, the Top Picks library. That library's folder is `...\programdata\data\top-picks`. For each pick the plugin makes a **copy** there. A copy is a folder of small files: a `.strm` file (a one-line text file holding the path of the real video, so Emby plays the real file), an `.nfo` file (a text file of details such as title, year, plot and age rating), pictures, and subtitles. Emby's Latest row puts the item with the newest **date added** first. So the plugin gives pick 1 the run's start time as its date added, pick 2 one hour earlier, and so on down to pick 10, nine hours earlier. That fixed start time is the **rank time**. It is in UTC (world time, not changed by the clocks going forward or back) and cut to the whole minute. The old plugin only wrote this date into the .nfo file. Emby reads that only the first time it sees a folder, which is why today's order breaks. The new plugin sets the date directly in Emby after every run and also writes it into the .nfo.

**When it runs.** Every Sunday at 05:00 server time (UK time), or when someone presses "Run now" in Emby's Scheduled Tasks or on the plugin's page. Only one run happens at a time. If Emby starts up and the last good run was more than 7 days ago, it runs once, 10 minutes after start-up. That doesn't happen right after the first install, when there is no last run.

**How it picks the 10.**
1. Pins first, in the owner's order. There can be up to 10, and only whole films or series. A pin is skipped and shown as "missing" if the title has gone or none of its video files can be found. A pin doesn't have to be in the chosen libraries.
2. The rest go to the most watched titles in the last 7 full UK days before the run day. For the Sunday run that is the previous Sunday to Saturday. "Most watched" is counted in **viewer-days**: each person who watched a title on a given day adds 1. A binge of 6 episodes in one evening is still 1, and the same person on 3 days is 3. Episodes count towards their series.
3. "Watched" means one of three things that day: Emby marked it played, or the time watched adds up to at least half the running time, or at least 20 minutes when the running time isn't known. For a series this works per episode: minutes from different episodes don't add up.
4. Ties are broken by which title had something added most recently, then the newer premiere date, then the lower Emby ID number.
5. If fewer than 10 titles were watched, the spare places go to the most recently added titles ("filler"). With fewer than 10 possible titles, the row is just shorter. Candidates are films and series in the chosen libraries (by default every film and TV library except Top Picks). A series counts if at least one of its episode files can be found, and missing episodes are left out of its copy.
6. Always 10: this can't be changed.

**What it does to files.**
- Each copy folder is named `Title (Year)`, with characters Windows doesn't allow removed. A clash with any existing folder gets ` - 2`, ` - 3`. Windows' reserved names (CON, PRN and so on) get `_` added.
- A film copy gets: `.strm` and `.nfo` files, subtitles (keeping endings like `.en.forced.srt`), `fanart.jpg` (the backdrop), `logo.png` and the theme video or song (copied only the first week). It also gets `folder.png` and `thumb.png`, which the plugin draws itself at 1000×562. The picture is the backdrop, black on the left 22% fading to clear by 40%, a huge white number in the Anton font, and the title's logo in the lower right part. With no logo, the title is written in white. With no backdrop, the poster is shown on black. If drawing fails, the plain backdrop is used and the report says so. The three reference pictures match this layout.
- A series copy gets `tvshow.nfo`, then `Season N` folders (`Specials` for season 0) with a `.strm` and `.nfo` for each episode, named `Series - SxxEyy - Episode title`, plus episode thumbnails and season posters.
- Every week, before touching the Top Picks folder, it builds the copies in a private "staging" (scratch) folder that Emby can't see. Then, in a fixed order: it deletes copies of titles that dropped out, updates copies of titles that stay one file at a time in the same folder (so Emby keeps the same item and people's watched ticks), and moves new copies in. It then asks Emby to rescan only the Top Picks library and waits up to 15 minutes (30 for a series with over 200 episodes). Next it sets each copy's date added directly (for series, the series and every episode), refreshes the pictures, and reads the dates back.
- **Safety.** The plugin keeps a "managed list" (managed.json) of the folders it owns. It only ever deletes folders on that list, and only after checking each one really is a plain folder directly inside top-picks and not a link (junction or shortcut) to somewhere else. Inside a copy it only deletes files it wrote itself, after the same kind of path checks. Anything else in top-picks (for example the owner's "Keep me" test folder) is never touched.

**How order is kept between runs.** An "order guard" runs after every library scan and 2 minutes after Emby starts. It puts back any date added that has drifted from its rank date, for series episodes too. It doesn't run while a run is actually working.

**Checking the row.** At the end of each run the plugin asks Emby for the Latest Top Picks row as an ordinary (non-administrator) user would see it. That user is set in settings, or by default is the first unrestricted non-admin. The plugin checks that its ranked copies appear in rank order. Unrelated folders in the row are listed as "extras" and don't fail the check. If the check fails, the plugin sets the dates and pictures once more and checks again. If it still fails, the run still counts as finished and the report shows the failure.

**Plays and watched.**
- The plugin records every film or episode that stops playing: who, which real title, which UK day, minutes watched and whether Emby marked it played. Plays on a copy count for the real title. These records are kept for 90 days in plays.json, on the server only, shown only to administrators.
- On the first run it imports the last 7 days from the Playback Reporting add-on's history (read-only), so the first list isn't empty. If that can't be read, it uses each person's "last played" dates instead.
- When someone finishes or part-watches a copy, the plugin marks the real film or episode watched (or copies the resume point) for that person. Marking a copy watched or unwatched by hand is copied too. New copies show the tick for anyone who has already seen the real title.

**Settings page and report** (administrators only):
- Settings: libraries to choose from, the row-check user, pins (search, add, drag to reorder, remove), Run now and a "run in progress" sign.
- Report: when the last run happened and how it ended (finished, incomplete or failed). For each title, its rank, why it was picked (pinned, X viewer-days or filler), and whether its copy and date were applied. Also the row-check result, plays in the last 7 days, missing pins, failed pictures, refusals with what to change, and the plugin and Emby versions.

**When it refuses to run:**
- the old plugin is still loaded (then it does nothing at all: no runs, no play logging, no watched copying);
- no library uses the Top Picks folder;
- the library's .nfo reader is off, or an .nfo saver is on;
- managed.json is damaged;
- a data file was written by a newer version (then it also stops writing any of its files).

A damaged play log or run record is renamed and a fresh one started.

**Taking over from the old plugin.** On the first run, any folder in top-picks containing at least one .strm and one .nfo (counting subfolders) is treated as the old plugin's and added to the managed list. It is linked to its real title through the path in its .strm file. Old folders for titles that are no longer picks are deleted. An old folder for a title that is still a pick is deleted and replaced by a fresh copy. Old pins are re-entered by hand.

**The proof plugin.** Before the Emby-facing part (chunk 4) is accepted, a separate tiny plugin, "Top Picks Proof", is installed next to the old plugin. It proves three things on the real server:
- (a) a plugin built this way loads in Emby 4.10.2;
- (b) whether Playback Reporting's times are UTC or local, and what its IDs look like;
- (c) in a throwaway test library at `programdata\data\top-picks-proof`, how Emby reads an .nfo date added in summer and in winter.

It never touches the Top Picks folder or row. The owner copies its page into the chat, then uninstalls it and deletes the test library and folder.

**Failure handling.**
- An error during a run while Emby stays up: the run is resumed 5 minutes later.
- A restart during a run: the run is resumed 2 minutes after start-up, with the same picks and rank time.
- At most 3 resumes after the first try, then the run is marked failed.
- Each step is safe to repeat. The progress is saved in run.json at every step.
- A run whose rescan wait runs out is "incomplete". It still counts as a good run, and the order guard finishes the job when the missing copies appear.

**Build order.** Each chunk is on its own branch, with CI (the automatic GitHub build) passing and a fresh review before it is merged:
1. Logic: all the rules as pure, testable code, plus CI additions: a Windows test job, pinned .NET version, and "mutation testing", which deliberately breaks the code to prove the tests notice.
2. Storage: data files, staging, swap, deletes, takeover file work.
3. Artwork: the pictures, with three samples for the owner to approve.
4. EmbyLink: everything that talks to Emby. It starts with the proof plugin, whose results must be in before chunk 4 is kept.
5. Settings page and report.

Nothing of Top Picks Plus goes on the server until all five are merged and released as v1.0.0.

**Go-live day:**
1. Remove the old plugin's scheduled triggers.
2. Make a "Keep me" folder with note.txt in top-picks.
3. Install Top Picks Plus with the old plugin still installed and restart. Check it does nothing and asks for the old one to be removed.
4. Uninstall the old plugin, restart, press Run now straight away, then do the remaining checks.
5. To undo that day: uninstall Top Picks Plus, reinstall the old plugin from the Desktop backup and restore its Sunday trigger.

## 2. What I would have to guess

### Blockers

**1. Blocker – Plugin-owned flags live where neither Storage nor Logic can reach them, yet automatic checks for them are given to Storage.**
Files: data.md (Settings table: `TakeoverDone`, `PlaybackReportingImported`, `ListeningSinceUtc`); D38, D80, D85, D91; Storage README ("plugin settings … via the project root" does not belong); src README walls (Storage must not use project root); checks C48, C78 (both listed under chunk 2 – Storage); D79 (no fake-Emby tests).
- The three flags are stored in Emby's plugin settings XML, which is `PluginConfiguration` in the project root. Storage is forbidden to use the project root, and Logic can't see it.
- C78 (Automatic, chunk 2) requires "`PlaybackReportingImported` and `TakeoverDone` end true". C48 (Automatic, chunk 2) requires "saving the settings page doesn't change TakeoverDone". Neither can be built or tested in Storage without crossing a wall, which needs the owner's approval.
- The import's "no double import" promise (D80) spans two stores (plays.json, then the XML flag) with no single owner.
- The usual Emby settings page saves the whole XML, so "the page never overwrites" needs a design: custom endpoints, or moving the flags into a Storage file. That design isn't chosen.
- D38's protection names only two flags, not `ListeningSinceUtc`.
- D85's "newer data stops all writing" covers only the three JSON files, not these flags.

Affects: F6 import, F9 takeover, D38, D80, D85, D91, C48, C78, C91; chunks 2, 4, 5.

**2. Blocker – A refusal found when a run resumes: D80, D68 and D85 give different answers.**
Files: D80 ("guards … a refusal is recorded and nothing else happens … The guards run again on every resume"); D68 ("A refusal condition found mid-run … stops the run as `failed` straight away"); D85 ("Storage then writes none of the three files"); D35/D51 (start-up with the old plugin loaded does nothing); data.md `lastRefusal` "never overwrites the run".
- For a resume that hits a guard (old plugin back, library missing, set-up wrong, managed.json damaged, data newer), a builder can't tell whether to:
  - record `lastRefusal` and leave the run waiting (D80), or
  - mark the run `failed` with `failReason` (D68).
- For `dataNewer`, D68 requires writing `failed` into run.json, but D85 forbids writing run.json at all.
- If Emby starts with an unfinished run while the old plugin is loaded, D35 says do nothing. It is undefined what happens to that run, and to `resumeCount`, once the old plugin is removed.

These are Logic rules in chunk 1 with automatic checks (C44, C72, C73, C77, C83). Whichever guess the builder makes gets written into the tests.

## 4. Confidence score: **75 / 100**

The documents are thorough and largely consistent. Every feature has checks. The chunks are assigned. The Logic, Storage and Artwork rules are exact enough to test. The reference pictures match the written layout. Earlier contradictions (resume counting, row-check extras, status order, go-live order) are now resolved and mostly marked. Two Blockers remain.

First, the plugin-owned flags sit in the Emby settings XML. The walls put that out of reach of the parts whose automatic checks depend on it (C48 and C78 in Storage), so a builder must either cross a wall or invent a design.

Second, D80, D68 and D85 disagree on what a refusal during a resume does, and for "data newer" they contradict each other outright. Those answers get written into chunk 1's tests.

Around these are eleven Should-fix gaps. The most important are the rank/state lifecycle in the managed list, the missing watched-state step, the loosely defined row-check queries, a proof plugin that may give no answer in winter, and an unspecified Stryker set-up.

None of this is large to fix, but a builder would have to guess on safety-relevant behaviour. That keeps the score well below 90.
